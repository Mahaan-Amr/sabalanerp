# Partner notification/duty adapter — #327

Consumes the `@sabalanerp/partner-sales-contracts@1.0.0` notification interface, also tested with the shared writer's compatible `1.1.0` package; notification wire `schemaVersion: 1`, `sha256-v1`. Runtime exports are injected through the public entry point; no manifest, schema, migration, route, shell, or activation changes belong to this lane.

## Integration contract for #334

1. #318 persists each committed inquiry cause and its immutable recipient/projection evidence. Call `planInquiryNotifications` with that cause and the transaction DB clock. `SUBMITTED` and `CANCELLED` target the responder; successful (including partial) batch decisions target the Partner; reassignment targets the Partner and newly assigned responder. Never include the previous responder as a substitute for current authorization. Retry the same cause identity, not a scheduler-run identity. The planner only emits safe references, not row errors, prices, names, or private record IDs.
2. Approval warning/expiry candidates are derived from the stored 48-hour interval; use a stable approval cause identity. A delayed warning is skipped at/after expiry. Missing a warning never changes validity. The inquiry owner remains the authority for approval use and must enforce DB time in every consumption transaction, independently of this module.
3. Supply `PartnerNotificationAccess` from #319/#318 and call `registerPartnerNotificationAccess` once before startup. `lockAndAuthorize` must serialize with assignment, grant, profile, ownership, and eligibility changes; verify the exact immutable notification and purpose; and reject obsolete warning/expiry causes. Its `canRead` and `resolveAction` must repeat the current root/purpose predicates, including historical-notice read rules after cancellation. The adapter adds recipient membership and active-user checks, but never implements a competing permission resolver. All Partner notifications fail closed while this provider is absent, including for Admin.
4. Construct `createPartnerInAppGateway(contract, sharedPrisma, access)`. Dispatch after the cause commits and retry failed results from the owner's durable source outbox. An advisory transaction lock plus existing unique event/recipient keys make concurrent delivery idempotent; reused identities with different intent are rejected. Notifications contain fixed Persian text, a null public reference, and the existing inbox URL. The shared action consumer can call `resolvePartnerNotificationAction` for a currently authorized destination; the destination must also authorize. No inquiry SMS, email, WhatsApp, Web Push, or realtime external payload is enabled.
5. Construct `createPartnerSupportDutyAdapter` with #318's locked unavailable-responder source. A missing/ineligible responder creates one existing SupportTicket per inquiry/assignment revision, with a safe tracking reference and authorized handlers only. This SupportTicket is the support task; do not also create a second CrossWorkspaceDuty or public price-response queue. No repeated broadcasts are sent. Support closure does not reassign an inquiry or authorize a response. The existing support lifecycle owns handling/closure; the source evidence owner retains the reverse mapping from the stable tracking hash to its inquiry/assignment for authorized remediation.
6. #315/#321 record the cancellation/void notice intent **with the committed Case transition**, using the original sent/verified snapshot and recipient evidence. `createCustomerCancellationNotifications` dispatches it **after commit** through the existing customer `NotificationGateway`, never the in-app inquiry gateway. Its `customerNotice` allowlist is only customer contract number, CANCELLED/VOIDED status, and the historical read-only link. The existing channel resolves the same allowlisted projection/recipient, enforces session access/expiry without successor redirect, and stores delivery receipts. #334 supplies `CustomerCancellationOutbox`: durable pending intent, append-only QUEUED/RETRY/SKIPPED history, idempotent downstream enqueue, retry scanning, and receipt linkage. An attempt/audit failure leaves the intent pending; no failure may be propagated back into the business transaction. Customer confirmation (`CUSTOMER_CONFIRMATION`) remains #325's responsibility.

## Acceptance boundary

Module/interface acceptance only. The existing notification and support tables are exercised with real PostgreSQL concurrency and namespaced fixture cleanup on `sabalanerp-local`. Central Partner authorization, inquiry/Case source persistence, customer channel receipts, and action-route binding require #334 integration, #335 combined QA, and #336 approval. No production deployment, real SMS, or activation is authorized.

Tests are in `backend/src/services/__tests__/partnerNotifications*.test.ts`. Run them with the repository's TypeScript runner (or the compiled JS equivalents in the existing local backend). Also run notification-policy/inbox, support-policy, and duty-authorization regressions, `npm run architecture:check`, and backend typecheck/build. Database tests require the existing local schema and may never target production; each owns and removes only UUID-namespaced fixtures.

The existing `notificationPolicy.test.ts` registry assertion adds only the six new expected names, under coordinator approval recorded in [#327](https://github.com/Mahaan-Amr/sabalanerp/issues/327#issuecomment-5436297836).
