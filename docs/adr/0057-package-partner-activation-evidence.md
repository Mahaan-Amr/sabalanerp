# Package Partner activation evidence behind one versioned interface

Partner release readiness, profile onboarding, and activation previously exposed separate operations whose ordering and exact evidence set could not be carried safely by the production management wire. We will use a deep `PartnerActivationPackage` module with one versioned query/execute interface and three staged commands—publish readiness obtained from a trusted verification adapter, bootstrap a pending Partner profile from existing owner-bound identity and policy evidence while enrollment is explicitly open, and atomically create a fresh immutable evidence bundle and activate after independent operations-v1 enrollment—so callers never construct readiness booleans or gate evidence and every owner decision, CAS check, idempotency result, audit event, and rollback remains fail-closed behind one seam. Cohort definition, enrollment-pause control, enrollment, and operational resume remain distinct operations-v1 commands and are never side effects of bootstrap.

The staged interface is preferred over one Admin "activate everything" command because HR, Sales, Accounting, release, and operations evidence must remain separately attributable, and over a generic attestation registry because the initial production workflow benefits from a smaller interface. Existing management v2 and operations v1 remain compatible; activation uses an additive wire and append-only persistence. Publication keeps enrollment, operations, traffic, and real SMS closed. A generic database row or source tag is not verification provenance, sample identity is not verified identity, and neither `ADMIN` nor a release signature can bypass a failed gate.
