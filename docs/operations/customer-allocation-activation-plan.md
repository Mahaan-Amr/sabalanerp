NO-GO for activation, merge as a working feature, or production release.** This plan grants no permission to deploy and is not an alternative deployment controller. The source-share guard stays closed until a separately reviewed implementation and all applicable evidence below exist. Follow `developer-release-handoff.md`, `protected-maintenance-next-update.md`, `zero-data-loss-deployment.md`, and ADR-0039 for every release.

## Problem and boundaries

The proposed workspace submits one confirmed `sourceAllocations` plan containing receipt and independent-credit shares. Its transaction requires the currently deny-only `requireCustomerSourceSharesWithin`. The independent-credit writer represents a settlement with `creditItemId` and a null `treasuryTransactionId`. The historical production-425 schema requires that transaction ID and its generated reader returned P2032 for this representation. No UI-only change, migration count, environment flag, or successful mock can establish safe admission.

The last recorded protected release is `10f3862e76f859a71b50d29583ac2df770c651c2`; its committed Prisma model permits this nullable relation. That report is historical, not proof of the currently installed release or its full reader behavior. Before qualification the operator must independently identify the actual running and retained immutable images, source/build identities, migration ledger, recovery state and all readers and workers. Any missing or changed identity is NO-GO.

## Phase 1: reader-compatible predecessor, writes closed

1. Freeze a clean candidate and its git tree, Inquiry gitlink, migration catalog and immutable application images. Record the actual running and exact rollback image identities; do not substitute a client regenerated from source for the installed image. Keep all source-share command and database safeguards closed.
2. Before every Docker action, verify the target using `docker compose -f docker-compose.local.yml ps` or `npm run docker:local:ps`. In isolated database and storage targets within the existing `sabalanerp-local` project, restore and verify a fresh, appropriately authorized production-state checkpoint. Use its existing harness and isolated test data or transactions; do not create a parallel stack or replacement service. Confirm schema, migration ledger, counts, checksums and provenance before changes. Do not use or alter the live local or production data for test writes.
3. Exercise actual retained-image application readers, API routes, jobs, reports, audit and recovery paths against representative old-format data and separately constructed credit-funded rows. Include complete domain-written and reversed records, full customer-account reads, allocation/reversal views, financial evidence and exact balances. Synthetic rows alone establish shape, not valid ledger behavior. A generated-client query alone is a preliminary diagnostic, not acceptance. Identify any reader that requires the old non-null representation; retire it with proven completion or supply a reviewed compatible predecessor. Verify already-open browser forms and retained browser assets against the changed API and draft recovery rules.
4. If the actual rollback release cannot safely read the new representation, prepare a reader-compatible **deny-only** predecessor as a separate protected release and qualify it before any activation release. Do not enable new writes in that predecessor. Confirm the precise compatible predecessor is the immutable rollback target for the subsequent candidate, including workers and supported browser builds.
5. Rehearse the required populated migration, protected update and injected rollback with exact immutable candidate and predecessor images. Verify local and independent remote checkpoint readback, leases, maintenance, drain, complete health gates, immutable image custody, recovery drill and fail-closed reopening. Before mutation, a failed attempt may reopen only the proven unchanged release. After mutation, restore the verified checkpoint under the original lease; retain maintenance whenever recovery cannot be proved. Existing protected procedures determine authority and execution; no force, bypass, partial promotion or mutable-image rollback is permitted.

## Phase 2: separately reviewed activation

1. Design and review a narrowly owned successor to the deny-only command barrier. First inventory every caller and direct/internal writer: the guard also covers receipt parts, resolution and correction, check bank and endorsement, opening attribution, compound commands, credit allocation and reversal. Grouped allocation reaches the guard again inside compound and credit writers. Admission must remain deny-by-default for every unrelated operation and be established at the canonical protected release boundary, tied to exact identities and evidence, and fail closed on absent, inconsistent or stale prerequisites. Test each non-authorized path, including replay after closure. No request parameter, process-only flag or skipped guard may grant activation. The retired online staging controller is not an available authority.
2. Prove real authenticated grouped allocation with multiple receipts and independent credit, including one-rial precision, permission checks, accounting-period/rule validation, atomic failure, complete ledger and audit evidence, and duplicate keys and changed payloads. Exercise concurrent grouped requests sharing receipt, credit and debt; mixed legacy and grouped writers; same-key races; serialization/deadlock retry; and all-or-none reconciliation. Test existing single-source, reversal, refund and correction behavior and relevant reports. Exercise UI and actual server/database paths, including in-flight forms, same-payload/key retries across deployment, ambiguous responses, definitive closed/409 responses, failed refresh and retained unsaved input.
3. Design an authorized durable command-status or equivalent recovery path for a committed command whose response was lost before rollback or closure. The current guard runs before the compound idempotency lookup, so closure prevents the ordinary retry from retrieving its prior result. Test commit → lost response → rollback/closure → same-key retry or status → exactly one posting. Any read-only reconciliation must authenticate and authorize the owner, verify the payload hash, and perform no new financial mutation; do not indiscriminately move retries ahead of the guard. Credit-funded reversal also invokes the guard: provide and qualify an authorized correction/reversal path throughout activation and compatible rollback, or another explicit safe disposition before activation. Test posting, rollback, reversal and reconciliation without stranding financial evidence.
4. Exercise the actual candidate and qualified predecessor on populated data including newly accepted grouped writes. Prove candidate admission and rollback/recovery preserve all acknowledged writes, allocations, vouchers, audit evidence and business files; prove old supported clients can read or safely retain drafts. During the original protected maintenance, prohibit production business/application writes between checkpoint and final gate; canonical controller-owned migrations and reconciliation and required isolated read/write smoke gates with deterministic cleanup remain subject to the existing procedure. A post-mutation failure restores the verified pre-mutation checkpoint under the original lease. After public reopening, any later rollback is a fresh protected operation with a freshly verified checkpoint of current data and a qualified compatible predecessor. Never replace acknowledged post-activation writes with a pre-activation checkpoint. If a compatible current-data recovery cannot be proved, remain in maintenance and fail closed.
5. Independently review standards and spec, repair findings, rerun affected tests, freeze the final clean candidate, and hand off exact identities and evidence. Run candidate-specific protected release and recovery gates; normal lease, local and independently verified remote checkpoints, full health gates and immutable rollback remain unchanged.
