# Grouped customer allocation GO decision

`deploy/scripts/lib/customer-allocation-go-manifest.mjs` verifies a version 1 Ed25519 signature over canonical JSON. Its public interface takes the signed payload, independently observed release facts, and a pinned independent approver public key and key ID. It returns a manifest hash only when the decision is `GO`, the operation is `GROUPED_ALLOCATION`, all exact identities and evidence hashes agree, the decision is at most five minutes old, and the observed protected phase and lease are live. The evidence map requires reader, populated QA, and rollback receipts; the cohort hash binds the approved population. Candidate and predecessor image maps must each contain exactly backend, frontend, and inquiry and match the observed maps exactly.

This is an offline verifier, not an activation command. The three manifest image roles describe application images. They do not replace the protected controller's separate custody checks for all six service images and the rollback set. Its `observed` argument is only trustworthy when the protected controller obtains it from immutable installed image custody and a single locked `deployment_operations` row, then samples `clock_timestamp()` after the lock. The controller must also compare the target commit and release identity, recheck the evidence artifact hashes and independent approval key custody, and ensure no other application or process can construct an activation decision. A caller supplied observation object is not authority.

The activation seam is the existing protected `deploy/scripts/deploy.sh` path immediately after `MIGRATIONS_APPLIED`, before release start. Under its drain, verified checkpoint and live lease, it must call the verifier and conditionally change a controller owned durable control row in the same database transaction as the locked operation check. That requires a new migration replacing the current `CHECK (state = 'CLOSED')` and immutable trigger with narrowly granted controller transitions and audit evidence, a transaction scoped runtime guard tied to build attested image identity, a closure path, and a release health gate comparing row, receipt and effective runtime identity before `TRAFFIC_OPENED`. Qualify the exact predecessor rollback reader and populated data rehearsal before this work is admitted.

The installed precursor control row is structurally `CLOSED`; `requireCustomerSourceSharesWithin` still rejects every posting. No environment variable or request can activate it.

## Dormant controller transition increment

Migration `20261116133000_customer_allocation_controller_transition` permits a single audited `CLOSED` to `ACTIVE` transition through two security-definer functions. The first function locks the exact deployment operation and control row, then samples the database wall clock. The second rechecks the production operation, exact lease and release, `MIGRATIONS_APPLIED`, a lease with more than 20 seconds remaining, unexpired decision, and unchanged `CLOSED` state before writing the receipt and audit row. Replay and direct control writes are rejected. Both functions require an exact `sabalan_allocation_controller` database `session_user`; the migration creates that role as `NOLOGIN` without a password. The dormant JavaScript controller keeps the row lock across signature verification and transition in one transaction.

This increment has no deploy-script invocation and no runtime admission change. The SQL activation function accepts a caller supplied manifest hash; it does not verify a signature or evidence. Only the dormant JavaScript controller verifies those inputs, so a distinct trusted controller credential and a protected invocation path are mandatory before activation. The migration creates a `NOLOGIN` role and rejects an existing role with elevated attributes, a password, or memberships. The JavaScript adapter requires the exact login as both session and current role, without elevation or memberships, before locking. It rolls back if the returned state and manifest hash differ from the verified decision.

Before wiring the controller into the protected release, the operator needs a separately provisioned controller credential, a pinned independent Ed25519 key ID and public key, immutable installed-image and evidence custody values for the verifier, and a non-superuser application database identity that cannot assume or change the controller authority. Both local and production Compose currently build the backend `DATABASE_URL` with the PostgreSQL bootstrap `POSTGRES_USER`; production's `sabalanerp` application role is a superuser and can assume the controller role. This topology does not establish controller-only security. Local role tests prove ordinary SQL denial, not resistance to a superuser credential.

The adapter requires a second, dedicated connection opened with the exact database configuration to be installed for the backend. It matches that connection's PID and role against the controller's PostgreSQL activity catalog on the same database. Admission rejects elevated attributes, role memberships, ownership or effective access to protected tables, schema or database creation privileges, and executable public security-definer functions other than the exact runtime admission function. Keep the second connection open for the decision transaction. The eventual protected invocation must bind its configuration to the exact backend being released.

## Protected closure

Migration `20261117140000_customer_allocation_controller_closure` restores the control row to `CLOSED` under the controller role and a locked live deployment operation in `MUTATION_STARTED` or `ROLLBACK_STARTED`. The operation must have its own verified local and remote checkpoint. Closure compares the exact activation digest under the same control row lock used by grouped writes. It appends an immutable closure receipt, preserves the activation receipt, and returns the same receipt when the exact closure is retried. A unique activation receipt per deployment and release prevents reusing that operation to reopen the control. The API expects the protected deployment runner to supply the exact checkpoint, lease and active digest. Runner wiring and qualification of reversal with the exact retained image remain pending.

## Runtime admission

Migration `20261117150000_customer_allocation_runtime_admission` checks the control row and the matching activation receipt under a transaction-scoped row lock. It permits grouped posting only for the dedicated non-elevated application role, the active release ID and the commit baked into the backend image, after the operation reaches `TRAFFIC_OPENED` or `COMPLETED`. The deferred grouped-child trigger independently checks database role and serving authority. Every other source-share admission operation remains closed. The migration creates the application role without a login or business grants. Provisioning, wiring the protected runner, and testing a real authenticated permitted posting remain separate outstanding work.

The migration-history health gate defaults to proving the control is closed. For an activation release, the protected runner must pass `DEPLOYMENT_CUSTOMER_ALLOCATION_MANIFEST_SHA256` from its verified activation receipt along with the existing deployment identity and lease. The gate then requires the matching activation audit, release and commit, `RELEASE_STARTED` phase, live lease, and verified checkpoint. This pre-traffic check is read-only. It leaves the runtime posting check closed until traffic opens. The protected runner supplies the receipt hash during an activation release.

## Evidence custody

The Linux allocation controller reads `decision.json`, `cohort.json`, `reader.json`, `populated-qa.json` and `rollback.json` from one canonical directory accessible only to the controller's host user. It checks ownership, file type, link count, access mode and file identity across each read. The controller computes SHA-256 from the evidence files and compares the digests to the signed decision. Candidate and predecessor image identities still come from the protected runner's installed-image inspection. The approver key is pinned separately. The evidence hash binds the reviewed bytes to the decision, while qualification of the actual evidence is the independent approver's responsibility.

## Isolated credential configuration

The qualification overlay `docker-compose.database-role-split.yml` renders a separate bounded URL for the backend and for the protected deployment service. The allocation controller credential is supplied only to its dedicated process. Its database adapter requires all three URLs to target the same database with separate login names and rejects a runtime or allocation-controller login that uses the bootstrap identity. Render checks verify that the backend receives no privileged credential and neither service receives the allocation controller credential. The runner requires a separately qualified predecessor using the same restricted application database configuration. First-time role provisioning and role-aware restore require their own protected qualification.

## Protected runner activation

Activation requires a separately qualified deny-only predecessor that already uses the restricted `sabalan_application_runtime` login and has the same migration catalog. The predecessor has to run against the already-provisioned controller role/schema. Installing the migrations, splitting login authority, and qualifying restoration of that split must be completed in separate protected work before requesting activation. Production Compose keeps the historical PostgreSQL defaults when the role settings are absent. The settings for a prepared split are `BACKEND_DATABASE_USER`, `BACKEND_DATABASE_PASSWORD`, `DEPLOYMENT_DATABASE_USER`, and `DEPLOYMENT_DATABASE_PASSWORD`. Compose inserts the credentials into URLs, so the values must be URL-encoded.

The protected operator supplies these settings for the ordinary protected runner:

- `DEPLOYMENT_CUSTOMER_ALLOCATION_EVIDENCE_DIR` is a new private absolute host directory containing `cohort.json`, `reader.json`, `populated-qa.json`, and `rollback.json`. The runner adds `request.json` before maintenance. The independent approver adds `decision.json` atomically while the runner is waiting after migration and reconciliation.
- `DEPLOYMENT_CUSTOMER_ALLOCATION_AUTHORITY_DIR` is a different private absolute host directory. Its `authority.json` contains `allocationControllerUrl`, `keyId`, and `publicKeyPem`. It carries the public key and the separate PostgreSQL controller login.
- `DEPLOYMENT_CUSTOMER_ALLOCATION_APPROVER_SHA256` is the independently pinned SHA-256 digest of the exact UTF-8 public key PEM string. Obtain this independently of the decision and evidence directory.

The directories must be owned by the protected runner's Linux user and accessible only to that user. Each input file must be regular, singly linked, and accessible only to that user. Use a fresh evidence directory for every attempt. The controller reads and hashes the same bytes it verifies. Ordinary releases with no activation evidence directory continue to require a closed allocation control.

The reader evidence also carries `predecessorCommit`, `predecessorMigrationSha256`, `predecessorScannerImage`, `predecessorScannerContainerId`, and `predecessorBrowserBuildId`. The runner compares them to the actual running immutable predecessor, including its scanner container and compiled frontend identity. The migration digest is SHA-256 over the compact JSON object mapping lexically sorted migration names to the SHA-256 of their exact SQL bytes. The candidate checks that its baked build commit and migration catalog match the request before invoking the controller transaction.

The protected runner compares the proposed backend database URL to the exact URL already installed in the serving backend. It also requires the deployment control URL to authenticate with the established PostgreSQL bootstrap credentials on that database. It records the effective role configuration fingerprint in a private operation file under the host lease. Recovery and rollback require that same fingerprint before privileged database work or runtime restart. An interrupted operation with a missing or changed fingerprint requires controlled recovery. A first-time database role split still requires separate qualification.

The runner checks the current allocation control before ordinary promotion and again before mutation. An active control blocks promotion of another release until verified current-data rollback closes it. Capture-only can still checkpoint the exact running release.

After the locked activation transaction returns its verified digest, the runner records the sealed decision’s exact predecessor backend, frontend and Inquiry image IDs and the reader’s scanner identities in recovery coordination before starting the new application. Canonical storage preflight reads that reference independently of checkpoint age. Current-data rollback requires the reference to match the retained signed evidence and installed images. Only a completed protected closure and rollback retires the live reference, and a retirement failure leaves the images protected.
 The dedicated controller process checks the role on the same PostgreSQL server using that URL and keeps the separate controller credential out of the application and normal deployment services. The runner checks the newly serving containers against the candidate images, stopped predecessor scanner, runtime configuration and release identity before using the receipt in the mandatory gate. The gate requires the matching protected operation, activation audit, checkpoint and actual PostgreSQL sessions from the backend container under the restricted role. Missing or mismatched authority takes the existing protected failure path. A successful source-level test does not establish a qualified production release. Record the populated checkpoint, signed exact-image admission, and rollback rehearsal before any production activation.
