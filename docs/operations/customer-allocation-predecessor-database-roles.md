# Scanner-retaining customer allocation predecessor database roles

The protected predecessor supports an already-provisioned database split. Use the same bounded URLs as the later allocation candidate. Set `BACKEND_DATABASE_USER=sabalan_application_runtime`, `BACKEND_DATABASE_PASSWORD`, `DEPLOYMENT_DATABASE_USER`, and `DEPLOYMENT_DATABASE_PASSWORD` in the private Compose environment. URL-encode credentials interpolated into the URLs. The deployment login is the existing PostgreSQL bootstrap owner, which retains migration, checkpoint, and restore ownership. Preserve the same PostgreSQL service and database. The application receives only the runtime URL. The allocation controller remains `NOLOGIN`, with no password or allocation authority supplied to the application or deployment service. The predecessor retains ClamAV and still denies grouped source-share posting.

The protected runner compares the rendered runtime URL byte-for-byte with the existing backend container configuration when a split is present. Missing and mismatched configuration stops the rollout. Before reopening after startup or rollback, the one-off deployment service checks its authenticated owner session on the database, the backend container's live runtime sessions, role attributes and memberships, effective grants and ownership, and the `CLOSED` allocation control. The check prints a redacted result. A legacy release with the existing bootstrap-backed URL is ineligible for split-role qualification.

## Separate first cutover and recovery qualification

The ordinary predecessor release cannot change the runtime URL or provision the controller. Before attempting the protected role cutover, establish all of the following under a separate approved operation.

1. Freeze the exact scanner-retaining release images and migrations, and resolve the existing bootstrap database owner and runtime container URL. Preserve the six-service rollback graph, scanner state, the private previous environment, and the original image and runtime identities. Acquire the canonical maintenance boundary, checkpoint, remote readback and lease before any role, ACL, or environment mutation.
2. Require the migration-created runtime and controller roles with no elevation, role memberships, or existing credentials. Keep the allocation controller dormant. Give the runtime role a unique credential held in the runtime URL and only reviewed per-object business privileges proven by the release's API, jobs, reports, audit and recovery entry points. Keep migration history, deployment operations, allocation control and allocation audit private. Deny runtime schema and database creation, ownership of persistent objects, and exposed privileged functions except the exact allocation runtime predicate. Keep recovery ownership with the bootstrap role. No credentials belong in a receipt or shell argument.
3. Qualify the exact restored role boundary before permitting split traffic. Reconstruct the reviewed runtime and controller ACLs in the staged database before promotion, verify the correct owner on all protected objects, and prove the same isolated PostgreSQL login cannot read protected tables or run controller entry points. The prepared-split protected runner applies the role snapshot described below. Its predecessor runtime gate must fail where authority cannot be proven.
4. Under the same protected operation, rehearse interruptions and rollback before and after role changes. Recover the exact prior runtime configuration, object ownership and grants together with its database, independently verified checkpoint and image set. On a failed protected rollback or unknown credential/configuration state, keep maintenance closed and follow controlled recovery. Verify real old and credit-funded allocations and acknowledgments, audit and exact balances with no source-share writes admitted. Record exact release, migration, browser, scanner, role, checkpoint and rollback evidence before requesting allocation activation.

The local opt-in database-role integration test uses the existing namespaced `sabalanerp-local` PostgreSQL fixture and a short-lived runtime-only credential. Its proof covers SQL authority and a genuine authenticated runtime session. It does not prove a first role cutover, a populated exact-image protected rehearsal, or production eligibility.

## Host configuration transaction for the first split

The private host transaction in `deploy/scripts/predecessor-role-host-configuration.py` is an interface for the protected lifecycle owner. The owner must retain the canonical deployment lock on FD9 and authenticate the active PostgreSQL lease, maintenance marker, exact local and remotely read-back checkpoint, installed six-image graph, and preserved ClamAV selection. The dormant ACL staging receipt is bound to that operation, checkpoint and original database. The lifecycle owner must also authenticate runtime login activation on that database before calling the host transaction.

The owner supplies the same generated 32-byte runtime secret as 43 unpadded base64url bytes on a sealed Linux memory file descriptor. The host activation interface passes the sealed credential and staged ACL digest on standard input to the dedicated one-off control command. This command checks the live lease, exact checkpoint and six-image graph, and applies a SCRAM verifier under the staged ACL receipt. It verifies that PostgreSQL rejects a different credential and that the intended credential authenticates without protected-table or database-creation authority. The runtime role is a PostgreSQL cluster-level login. The credential proof covers the checkpointed source database. Any other database's connection and access policy must be reviewed with the exact host during rehearsal. The protected runner keeps its maintenance hold after activation. The canonical runner still needs a same-image continuation that binds the host receipt to the live backend and authorizes traffic only after its normal release or rollback gates pass.

The transaction appends only the two runtime Compose settings and privately renders both configurations to confirm that the owner URL, pool settings, database, images, mounts and all other settings match. The deployment service's checkpoint runtime-role selector follows the new runtime username. The owner remains responsible for recreating the backend with the exact image and for proving its authenticated restricted sessions before any reopening.

Before the environment is replaced, the transaction durably records its exact prior bytes and the expected target binding in a private operation directory under `.deploy-state`. A separate receipt carries only operation and graph identities, checkpoint and staging digests, and the transaction state. If replacement succeeds and receipt publication is interrupted, enter the owned `ROLLBACK_STARTED` boundary and restore from the private record before invoking the legacy checkpoint restore. The database rollback command requires all runtime sessions to be drained, verifies the active credential against its private operation binding, then restores the dormant role and prior ACLs in one transaction. If the current environment matches neither the previous nor the target bytes, or the original rendered configuration cannot be verified, keep maintenance closed for controlled recovery. The lifecycle owner must retain the private record until rollback or reopening is proven, then dispose of it as credential-bearing material.

## Protected configuration release sequence

Deploy and qualify the scanner-retaining predecessor on the original database role first. The first role cutover is a separate protected configuration release on that already-serving image. It takes its own fresh verified checkpoint and uses the exact source, migrations, browser build, and six images already in service. It must skip source fetch, builds, migrations and broad service recreation.

The foreground adapter is callable by the existing protected owner after it reaches `MUTATION_STARTED` with the same inherited FD9 and an authenticated maintenance, advisory-lock, and database-lease boundary. It pins the preflight envelope and original environment, saves the native stage receipt, sends the sealed credential only to the dedicated login command, and uses the exact host configuration and runtime continuation interfaces. It binds the result to the native live PostgreSQL proof. Under `ROLLBACK_STARTED` it can revoke the credential and recover the owned ACL preimage, then prove the original host configuration. If staging committed before its native reply was received, the live database transaction record can recover the ACL preimage. If no host environment snapshot was written, the owner proves the exact old environment from the earlier private binding.

The native adapter wraps the canonical owner's selected control and Compose command vectors under FD9. It renews the same lease and drains native output until the original child and both pipes close, including after a failed renewal, deadline, or interruption. It passes the credential only on standard input. Its durable intent and closure receipts carry operation and checkpoint identities and process status without command arguments, output or credentials. A clean closure supplies private stdout to the choreography. Neither closure nor an interrupted receipt authorizes release.

The import-only canonical adapter uses the existing one-off control transport, verifies the original advisory session, and renews the same lease. It distinguishes the serving release identity used for backend recreation from the operation identity used by control commands. Its nginx refresh restarts the original pinned container ID, proves the new process birth and health, and checks both public maintenance endpoints before emitting a receipt. No refresh retries an unknown attempt by restarting again.

The canonical runner exposes preflight only. A future protected launcher must enter the owned, already-checkpointed configuration phase and attach this adapter as the foreground continuation. The continuation starts only the pinned original frontend and Inquiry containers, then runs the applied or rollback gate inventory through the same lease. Its gate acknowledgement binds the report to the checkpoint, original scanner graph, live backend, original nginx refresh and closed native gate child. The gate modes preserve the database ACL and credential rollback receipt. Terminal publication and hold release still require their own durable ownership and external traffic readback.

The terminal custody interface records an opening intent under FD9 before the owner can remove the maintenance marker. This intent blocks automatic rollback even if the original opening result was lost. A returning owner can read back an already-open operation with its live lease and both verified origins. It never repeats the marker removal. The two holds and opening intent are archived only after terminal database evidence, no active lease, no active host session and fresh readback from both origins. A partial archive can finish from the exact retained bytes. The dedicated deployment control commands authorise the exact held gate report, open against the durable intent, and finish once the two-origin host readback is available. They retain the ACL recovery state and support terminal journal recovery after a lost finish acknowledgement. The canonical host adapter attaches those commands to retained native children under FD9. It checks the pinned backend and refreshed nginx, verifies HTTPS independently at both configured origins, and reads a completed SQL row before archiving the holds. The public runner still needs to launch the dedicated same-image sequence and support controlled resumption of an interrupted terminal handoff.

## Role-aware checkpoint and automatic rollback

With `BACKEND_DATABASE_USER=sabalan_application_runtime`, the protected deployment service captures the runtime and allocation-controller role attributes, object owners and normalized PostgreSQL grants in `database/protected-role-acls.json`. It exports a PostgreSQL snapshot and imports that same snapshot in `pg_dump`. The component is covered by the encrypted COMPLETE package, its manifest and the protected checkpoint checksum. Passwords, credentials and executable SQL are excluded.

The supported topology uses the authenticated PostgreSQL bootstrap owner for control and object ownership, with PostgreSQL's public-schema owner also accepted. Both restricted roles must already exist. The role component supports database, public schema, relation, sequence and routine ACLs. Role memberships, ownership by restricted roles, custom database connection limits, default, column or type ACLs, large objects and additional user schemas fail capture or verification. Capture and restore also check that the restricted roles have no protected-table or create authority and that the runtime cannot execute controller security-definer functions.

Local checkpoint validation and automatic rollback apply and read back the captured ACLs inside a private staged database. Automatic rollback requires the owned maintenance marker, active host session, the live `ROLLBACK_STARTED` PostgreSQL lease and the exact verified checkpoint recorded in the deployment row. It restores the archived schema and security-definer ownership under the same PostgreSQL owner. Promotion atomically switches the database names, keeps the old safety database private and reopens the promoted database for its restored runtime login.

Legacy deployment checkpoints remain supported for the bootstrap-backed topology. A restricted-role rollback requires its ACL component and matching cluster role configuration. Generic backup and restore keep their ACL-free behavior for historical packages. The owner-only automatic rollback does not provision logins, perform the first credential split, or qualify independent disaster recovery. The independent drill requires a separate role-aware qualification before a restricted-role checkpoint can count as a verified independent recovery point.

## Protected control commands for ACL staging

The first ACL staging step uses the one-off deployment service in `/app`, with the authenticated bootstrap owner, the exact immutable control image and the usual protected host lock. Use `node dist/scripts/deployment-control.js prepare-predecessor-role-cutover` to bind the intent to the protected session. The host must establish public maintenance on both origins, drain the original services, verify the complete checkpoint locally and against its independent remote copy, and enter `MUTATION_STARTED` through the existing lease and journal transitions before calling `node dist/scripts/deployment-control.js stage-predecessor-role-grants`. The normal release runner does not invoke this command.

The command checks the live lease, ordered local journal, verified archive identity recorded on the lease, matching canonical checkpoint sidecars, local archive checksum and remote file fingerprint. It checks the exact PostgreSQL instance and database identity and the absence of other database client sessions and prepared transactions. It validates the pinned migration and ACL catalog with both roles dormant. It applies the reviewed grant changes and records hashes of the prior and staged normalized PostgreSQL ACLs, their object identities, and the checkpoint binding in the owner-only deployment row in one transaction. A retry under the same operation returns the original binding only if the staged catalog still matches. Save the redacted JSON response with the host operation evidence.

For the reverse step, enter `ROLLBACK_STARTED` and invoke `node dist/scripts/deployment-control.js restore-predecessor-role-grants` with the same host and checkpoint binding. It requires the recorded staged state, reverses the same ACL changes, and verifies the original hash before committing. A missing receipt, changed ACL, changed database identity or unknown operation state requires controlled recovery with maintenance held. Both commands leave the role credentials and runtime configuration intact. This staging step does not yet authorize reopening maintenance, a first runtime login, ordinary release promotion, or production cutover.
