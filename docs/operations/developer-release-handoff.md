# Developer handoff before a protected release

Use this on every device when synchronizing work and before handing a candidate to the production operator. The production deployment procedure is in [the next-update runbook](protected-maintenance-next-update.md) and [the protected controller contract](zero-data-loss-deployment.md).

1. **Preserve local work.** Record the checkout path, branch, `git status --short --branch`, `git rev-parse HEAD`, and `git submodule status`. Commit intentional work on its own branch or keep a named patch/worktree. Do not reset, clean, or overwrite uncommitted files to make a pull succeed. Keep secrets, private backups, QA data, and generated artifacts out of Git.
2. **Refresh and reconcile.** Fetch `origin` and inspect `origin/main` plus every developer branch intended for the release, including the coworker's branch. Compare commits and file changes against the running production commit. Explicitly decide which changes are included, deferred, or already merged. Resolve conflicts in a separate integration branch; verify that no local-only business fix or migration was dropped. Do not treat a branch name or an old local tracking ref as a release identity.
3. **Freeze the candidate.** Publish one reviewed integration commit and record its full SHA, tree, clean status, and pinned `apps/sabalan-inquiry` gitlink. Recheck the remote SHA after push and require each participating device to fetch and confirm the same commit before calling the devices synchronized. Leave unrelated local work on its own branch. If the candidate changes, record the new identity and identify any results that apply only to the previous candidate.
4. **Apply the release owner's QA choice.** When the owner requests a production release and has given no QA choice, ask once and wait for their choice before starting product QA or protected deployment. Use the stated choice when supplied.
   - **Direct deployment** proceeds to protected deployment without running or waiting for product QA.
   - **Focused tests** runs a short list for the changed workflows. State the commands before running them.
   - **Full QA** runs the agreed suites for the exact candidate.
   - If selected tests fail, report the failure and obtain the owner's decision before proceeding. Record unrun suites as such.
5. **Hand off exact identities.** Give the operator the candidate SHA, included branch heads, Inquiry gitlink, migration inventory, selected QA, actual results, and known limitations. Review migration support, authorization and data impact, and compatibility with the retained release. Apply independent feature activation requirements. The operator confirms production identity and runs the protected deployment gates.

Completion means the published candidate and intended changes are accounted for, each participating device has verified the same remote commit, and the operator can identify precisely what to deploy. Synchronization alone does not authorize a production update.
