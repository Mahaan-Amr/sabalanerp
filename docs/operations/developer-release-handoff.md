# Developer handoff before a protected release

Use this on every device when synchronizing work and before handing a candidate to the production operator. The production deployment procedure is in [the next-update runbook](protected-maintenance-next-update.md) and [the protected controller contract](zero-data-loss-deployment.md).

1. **Preserve local work.** Record the checkout path, branch, `git status --short --branch`, `git rev-parse HEAD`, and `git submodule status`. Commit intentional work on its own branch or keep a named patch/worktree. Do not reset, clean, or overwrite uncommitted files to make a pull succeed. Keep secrets, private backups, QA data, and generated artifacts out of Git.
2. **Refresh and reconcile.** Fetch `origin` and inspect `origin/main` plus every developer branch intended for the release, including the coworker's branch. Compare commits and file changes against the running production commit. Explicitly decide which changes are included, deferred, or already merged. Resolve conflicts in a separate integration branch; verify that no local-only business fix or migration was dropped. Do not treat a branch name or an old local tracking ref as a release identity.
3. **Freeze the candidate.** Publish one reviewed integration commit and record its full SHA, tree, clean status, and pinned `apps/sabalan-inquiry` gitlink. Recheck the remote SHA after push and require each participating device to fetch and confirm the same commit before calling the devices synchronized. Leave unrelated local work on its own branch. Do not add new commits to an already qualified release without requalifying the changed candidate.
4. **Verify the affected behavior.** Review the complete diff from production, pending migrations and their protected-runner support, business-data and authorization impact, and compatibility with the retained release. Run the relevant build, architecture/design-system checks, focused behavioral tests, and browser or HTTP checks for changed user journeys. For a performance fix, measure the actual affected workflow and its data-loading requests against a representative population; a fast API response alone does not prove the page is fully loaded. Record commands, results, known failures, and any required candidate-specific acceptance evidence. Never label a skipped or failed check as passing.
5. **Hand off exact identities.** Give the operator the candidate SHA, included branch heads, Inquiry gitlink, migration inventory, test/evidence summary, and known limitations. The operator confirms the current production identity and runs the canonical storage, recovery, checkpoint, immutable-image, health, and rollback gates from the runbook. A full update/rollback rehearsal is periodic under that runbook, unless a candidate-specific gate requires one.

Completion means the published candidate and intended changes are accounted for, each participating device has verified the same remote commit, and the operator can identify precisely what to deploy. Synchronization alone does not authorize a production update.
