# Isolated Linux host for #432 rehearsal

The owner authorized one independent Linux host for the complete production-state-copy rehearsal in #432. This is the sole exception to the local `sabalanerp-local` project rule. The existing six local services, their data, and both #436 checkpoints remain untouched. Issue #439 owns host preparation; #438 reviews the QA controller and backup target, using the unchanged production runner wherever its exact identity and lease gates pass. Neither host provisioning nor a component restore qualifies #432.

### Snapshot-time source lease in the November 12 copy

The November 12 complete checkpoint was captured while its own source deployment held the database lease. Its exact copied row (`deploy-20261112T133543Z-b58c53c0f88d-release`) can therefore have `phase=SERVICES_DRAINED` and `activeKey=production` even though the later source postrun ended `ABORTED` and released the lease. Do not change the normal controller or classify the copied active row as a current QA deployment.

For each fresh retained-old-state restore, use `deploy/scripts/run-qa-restored-lease-reconcile.mjs` **once**, before the protected controller. Its eleven arguments are the same eight private paths/hashes as `run-qa-production-state-restore.mjs`, followed by the preserved root-owned mode-0400 QA target plan that originally authorized that restore, the root-owned mode-0400 `lease-reconcile-plan.json` in the restore run, and its SHA-256. The wrapper holds and verifies the normal host FD9 lock, validates the historical restore target plan against the immutable restore plan, separately reselects the current QA plan and rendered Compose graph, checks the source and receipt custody, invokes the QA-only control image, proves both loopback HTTPS origins return 503, then invokes the exact compare-and-swap. It leaves maintenance active on any failure. Never run this command on production or a different checkpoint.

The private reconciliation plan uses `sabalan-qa-restored-lease-reconcile/v1`, `qaOnly:true`, the exact source checkpoint ID/object and sidecar SHA-256, restore plan/report SHA-256, current QA target plan SHA-256, current QA kernel boot ID SHA-256, database name, copied row ID/release/commit/phase/timestamps and SHA-256 of its lease token (never the raw token), SHA-256 of a fresh authenticated read-only production terminal observation, and `receiptPrefix:"/qa-evidence/lease-reconciliation"`. It must independently prove the **same** source deployment ended `ABORTED`, has no active lease, was capture-only with no mutation and a verified postrun journal, and that the source checkpoint/restore hashes agree. The control script also verifies the QA-only environment, `.invalid` production URL, QA control database marker, current boot identity, restored report, source archive and sidecar bytes, no pending restore journal/controller, and exactly one active copied row with no unresolved blocker.

The script writes a private mode-0600 full preimage receipt before the transaction, then updates only that copied operation's phase, `activeKey`, completion and explicit QA reconciliation reason under a serializable transaction with advisory lock and exact row compare-and-swap. It reads back zero active/unresolved deployment rows and writes a separate private postimage receipt before removing its own maintenance marker. ## Private controller target

`docker-compose.rehearsal.yml` inherits the six production service definitions and the deployment control profile. Its application network is Docker-internal; backend, Inquiry, PostgreSQL, frontend, and the deployment control container have no external Docker network. ClamAV alone has a second egress network so its real updater and publisher health gates can run. Nginx alone has a separate QA ingress bridge: Docker does not activate published ports for a container attached only to an internal network. That bridge disables IP masquerading, and Nginx's two host ports still bind only to `127.0.0.1` inside the named QA network namespace. Verify the actual `docker port` result, namespace listeners, HTTPS and maintenance 503, and refusal of Nginx external egress before a controller run. This is a QA graph, not a production Compose replacement. The exact protected `deploy.sh` controller selects it only for a normal release with both `DEPLOYMENT_QA_REHEARSAL_PLAN_FILE` and `DEPLOYMENT_QA_REHEARSAL_PLAN_SHA256` set. ## Private network namespace qualification

The 2026-11-13 #439 network gate found that the QA and backup WSL distros and Docker Desktop share one initial network namespace. The native QA daemon currently runs there with `--iptables=false`. Do not turn on its iptables management in that namespace. Create a named `sabalanerp-qa` network namespace only after a separate review of the no-data procedure. Run the native QA `dockerd` and every protected controller invocation through `ip netns exec sabalanerp-qa`, retaining the ordinary host PID and mount views. Pin the named namespace inode in the private v2 plan after creation. A daemon restart changes its PID and must repeat the controller's existing PID/birth/FD9/pidfd checks; a namespace recreation changes the inode and requires a newly reviewed plan.

The proposed uplink is `slirp4netns` with a TAP interface in that named namespace, `--configure` and `--disable-host-loopback`, plus a namespace-specific resolver pointing to its DNS forwarder. Its user-space translation can carry ClamAV's direct HTTPS acquisition and live publisher TXT lookup while Docker's bridge and iptables rules stay in the private namespace. Keep the application bridge Docker-internal; only ClamAV gets `clamav_egress`, and only Nginx gets the non-masquerading `qa_ingress` bridge. Docker's published Nginx ports bind to `127.0.0.1` **inside** the namespace, so HTTPS probes and the protected controller must run inside it. Do not add a host-side port forward. The separate QA backup endpoint remains off-computer and must be reachable with independent readback from inside the namespace.

This source change is a fail-closed selector gate, not evidence that the uplink works. Before any image import, service creation, restore or rehearsal, independently review and run a bounded no-data namespace probe. It must prove distinct namespace inode for the initial WSL/Desktop network and the QA daemon; no change to the initial namespace's iptables, routes or bridges; direct DNS TXT and HTTPS from a temporary private-bridge probe; no host-loopback access; loopback-only ingress; and reachability of the independent QA backup endpoint. Stop on any failure. The existing six `sabalanerp-local` instances and both #436 checkpoints remain untouched. #432 remains NO-GO until the full protected runs pass.

Set `DEPLOYMENT_NGINX_BIND_ADDRESS=127.0.0.1` and private `erp.qa.test` / `inquiry.qa.test` origins in that environment. Resolve both names to loopback only on the QA host, install distinct QA TLS certificates in its isolated certbot volume, and verify real HTTPS 503 on both origins before a rehearsal. The backend's unchanged production-environment validator requires `SMS_IR_ENVIRONMENT=production`; therefore use a synthetic `qa-disabled-...` SMS key and `SMS_IR_API_URL=http://127.0.0.1:9` only with the Docker-internal network. Do not copy live SMS, push, biometric, or other delivery credentials. Allow only the specific application/recovery keys required to decrypt and verify the copied state. The backup SSH/SFTP owner and checkpoint root must remain independent of the production backup namespace; no checkpoint data goes to production custody for these QA runs.

The [#438 conditional design](../../reports/qa/protected-rehearsal-438-conditional-design-20261112.md) records the source blockers and exact image/key scope. Production `deploy.sh` defaults and ADR-0039 remain authoritative; any QA-specific target change requires independent review.

## Separate QA namespace on the physical backup host

The backup host may serve QA through a separate, reviewed root-owned bundle at `/opt/sabalanerp-qa-recovery`. Build it from the exact reviewed source after the QA retention selector is integrated, using `node scripts/build-qa-backup-host-pack.mjs --build --output <fresh-absolute-private-directory-outside-the-checkout>`. The QA builder packages only the four QA shell files, `storage-preflight.mjs` and its storage policy module, and a separately compiled `backup-checkpoint-retention.cjs`; it never alters the production host pack. Verify every output against `qa-backup-host-pack-receipt.json` and inspect the compiled retention inputs before transferring. Stage the verified output in a private host directory, then copy only that reviewed file set into a fresh `/opt/sabalanerp-qa-recovery` owned by root, with no symlinks, writable-by-other files, or production recovery paths. The provisioner refuses a missing owner bundle or any other bundle location.

Its QA-only provisioner is `deploy/scripts/provision-qa-backup-host.sh`. Supply two distinct, root-owned, single-link Ed25519 public key files as its arguments, in transfer then operations order. Stage public keys under `/root/sabalan-qa-backup-provision/transfer.pub` and `/root/sabalan-qa-backup-provision/operations.pub` on the backup host; keep private keys only under the QA controller's private custody. Independently review the bundle and commands before executing the provisioner as root. It must not be run from the production recovery bundle.

The QA transfer account is `sabalan-qa-backup`, forced into SFTP with chroot `/srv/sabalanerp-qa-recovery` and start directory `/checkpoints`. The separate `sabalan-qa-backup-ops` key accepts only `preflight <bytes>` or `retain`, through QA-specific sudo commands. Both owners use `/run/lock/sabalan-qa-backup-storage.lock` as FD9; the root retention wrapper selects `SABALAN_BACKUP_TARGET=qa` and requires the reviewed QA owner in the separate bundle. Its checkpoint root is `/srv/sabalanerp-qa-recovery/checkpoints`; its audit is `/var/log/sabalanerp-qa-backup/storage-cleanup.jsonl`. No QA SSH match or sudo rule grants access to the production backup account, command, bundle, lock, or checkpoint root.

Pin a distinct QA hostname for the same physical backup host in the private QA plan and known-hosts file, using the independently observed host key. Before provisioning, reject any QA root or checkpoint mount/bind alias to production custody. After reviewed provisioning, prove separate account identity and forced-command behavior with both keys, SFTP chroot/readback of a disposable QA object, QA root/lock ownership, and refusal of shell or unlisted operations commands. Observe production account configuration, nine retained checkpoints, root, and lock before and after. Capacity must be remeasured before each protected run; a QA checkpoint is not permission to prune production custody.
