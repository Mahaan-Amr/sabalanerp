## Private network namespace qualification

The 2026-11-13 #439 network gate found that the QA and backup WSL distros and Docker Desktop share one initial network namespace. The native QA daemon currently runs there with `--iptables=false`. Do not turn on its iptables management in that namespace. Create a named `sabalanerp-qa` network namespace only after a separate review of the no-data procedure. Run the native QA `dockerd` and every protected controller invocation through `ip netns exec sabalanerp-qa`, retaining the ordinary host PID and mount views. Pin the named namespace inode in the private v2 plan after creation. A daemon restart changes its PID and must repeat the controller's existing PID/birth/FD9/pidfd checks; a namespace recreation changes the inode and requires a newly reviewed plan.

The proposed uplink is `slirp4netns` with a TAP interface in that named namespace, `--configure` and `--disable-host-loopback`, plus a namespace-specific resolver pointing to its DNS forwarder. Its user-space translation can carry ClamAV's direct HTTPS acquisition and live publisher TXT lookup while Docker's bridge and iptables rules stay in the private namespace. Keep the application bridge Docker-internal; only ClamAV gets `clamav_egress`. Docker's published Nginx ports bind to `127.0.0.1` **inside** the namespace, so HTTPS probes and the protected controller must run inside it. Do not add a host-side port forward. The separate QA backup endpoint remains off-computer and must be reachable with independent readback from inside the namespace.

This source change is a fail-closed selector gate, not evidence that the uplink works. Before any image import, service creation, restore or rehearsal, independently review and run a bounded no-data namespace probe. It must prove distinct namespace inode for the initial WSL/Desktop network and the QA daemon; no change to the initial namespace's iptables, routes or bridges; direct DNS TXT and HTTPS from a temporary private-bridge probe; no host-loopback access; loopback-only ingress; and reachability of the independent QA backup endpoint. Stop on any failure. The existing six `sabalanerp-local` instances and both #436 checkpoints remain untouched. #432 remains NO-GO until the full protected runs pass.

Set `DEPLOYMENT_NGINX_BIND_ADDRESS=127.0.0.1` and private `erp.qa.test` / `inquiry.qa.test` origins in that environment. Resolve both names to loopback only on the QA host, install distinct QA TLS certificates in its isolated certbot volume, and verify real HTTPS 503 on both origins before a rehearsal. The backend's unchanged production-environment validator requires `SMS_IR_ENVIRONMENT=production`; therefore use a synthetic `qa-disabled-...` SMS key and `SMS_IR_API_URL=http://127.0.0.1:9` only with the Docker-internal network. Do not copy live SMS, push, biometric, or other delivery credentials. Allow only the specific application/recovery keys required to decrypt and verify the copied state. The backup SSH/SFTP owner and checkpoint root must remain independent of the production backup namespace; no checkpoint data goes to production custody for these QA runs.

The [#438 conditional design](../../reports/qa/protected-rehearsal-438-conditional-design-20261112.md) records the source blockers and exact image/key scope. Production `deploy.sh` defaults and ADR-0039 remain authoritative; any QA-specific target change requires independent review.

Its checkpoint root is `/srv/sabalanerp-qa-recovery/checkpoints`; its audit is `/var/log/sabalanerp-qa-backup/storage-cleanup.jsonl`. No QA SSH match or sudo rule grants access to the production backup account, command, bundle, lock, or checkpoint root.
