# Isolated Linux host for #432 rehearsal

The owner authorized one independent Linux host for the complete production-state-copy rehearsal in #432. This is the sole exception to the local `sabalanerp-local` project rule. The existing six local services, their data, and both #436 checkpoints remain untouched. Issue #439 owns host preparation; #438 reviews the QA controller and backup target, using the unchanged production runner wherever its exact identity and lease gates pass. Neither host provisioning nor a component restore qualifies #432.

## Host preparation boundary

1. Pin the Linux distribution source, disk location, Docker Engine version, and daemon configuration. Use a native daemon on the rehearsal host, with a socket and data root distinct from Docker Desktop. Verify actual daemon PID/birth, `/run/docker.pid`, root-owned `/var/lib/docker/containers/<id>/config.v2.json`, `/proc` FD9 flock, pidfd and shared kernel/PID view before creating QA services. Record the checks and stop if any fail.
2. Measure host and Docker data-root free space for verified previous and candidate image archives, full restored PostgreSQL/files, two checkpoint generations, independent readback, and safety reserve. Preserve the newest two healthy backup points and incident holds. A capacity failure stops before image transfer or service creation.
3. Create only the private six-service QA project with separate PostgreSQL, ClamAV, backend, frontend, Inquiry, and Nginx data. Use Compose project name `sabalanerp` on the distinct native QA Engine: this retains the existing protected controller's exact project and container identity checks, and cannot alias the Desktop `sabalanerp-local` project because the daemons, sockets, data roots, checkouts, and volumes are separate. Set `DEPLOYMENT_NGINX_BIND_ADDRESS=127.0.0.1` in the private QA environment, verify both rendered port bindings, and prove QA ingress cannot receive public traffic. Production keeps its all-interface default. Pin exact immutable previous and candidate image identities. Every QA mount, database, lock, marker, and key path is separate from production and `sabalanerp-local`.
4. Work from a size/hash-verified copy of the 2026-11-12 encrypted checkpoint and a distinct writable sidecar copy. Keep the original independent object and sidecar in custody. Supply the matching private recovery and application keys through reviewed private mounts; do not print or commit key bytes. Prove application payload decryption in the isolated restore.
5. Execute the real plan-bound protected controller through one complete candidate update and a separate injected post-mutation rollback on reset QA state. Record all lease, maintenance 503, local and remote checkpoint, image, migration, health, acknowledged-write preservation, and fail-closed receipts. #432 remains NO-GO until both runs and representative business writes pass.

## Private controller target

`docker-compose.rehearsal.yml` inherits the six production service definitions and the deployment control profile. Its application network is Docker-internal; backend, Inquiry, PostgreSQL, frontend, Nginx, and the deployment control container have no external Docker network. ClamAV alone has a second egress network so its real updater and publisher health gates can run. This is a QA graph, not a production Compose replacement. The exact protected `deploy.sh` controller selects it only for a normal release with both `DEPLOYMENT_QA_REHEARSAL_PLAN_FILE` and `DEPLOYMENT_QA_REHEARSAL_PLAN_SHA256` set. Its production default remains `docker-compose.prod.yml`.

The reviewed plan is a root-owned, regular, single-link mode-0400 JSON file outside Git. It pins format `sabalan-qa-rehearsal-target/v1`, `/opt/sabalanerp`, QA custody root `/srv/sabalanerp-qa`, machine ID, hostname, native Docker Engine ID, exact application commit/tree, SHA-256 of the QA Compose and private environment files, distinct QA and production backup hostnames, and the two `.qa.test` domains. Keep the private secret directory, remote checkpoint mount, reports, SSH keys, and known-hosts file beneath the QA custody root. The selector checks the clean checkout, `/var/lib/docker` Engine root, exact rendered service/network/loopback-port graph, every rendered mount source and target, canonical QA paths, and inherited shell variables before allowing any source fetch, storage cleanup, lease, or maintenance. Protected path values cannot contain Compose interpolation; symlinked custody paths and binds outside the QA root refuse. In QA, the plan-pinned checkout is used as-is; there is no remote Git change after selection. A missing, changed, non-root, or mismatched plan refuses. Capture-only, configuration, prebuilt, and scanner incident modes cannot select this target.

Set `DEPLOYMENT_NGINX_BIND_ADDRESS=127.0.0.1` and private `erp.qa.test` / `inquiry.qa.test` origins in that environment. Resolve both names to loopback only on the QA host, install distinct QA TLS certificates in its isolated certbot volume, and verify real HTTPS 503 on both origins before a rehearsal. The backend's unchanged production-environment validator requires `SMS_IR_ENVIRONMENT=production`; therefore use a synthetic `qa-disabled-...` SMS key and `SMS_IR_API_URL=http://127.0.0.1:9` only with the Docker-internal network. Do not copy live SMS, push, biometric, or other delivery credentials. Allow only the specific application/recovery keys required to decrypt and verify the copied state. The backup SSH/SFTP owner and checkpoint root must remain independent of the production backup namespace; no checkpoint data goes to production custody for these QA runs.

The [#438 conditional design](../../reports/qa/protected-rehearsal-438-conditional-design-20261112.md) records the source blockers and exact image/key scope. Production `deploy.sh` defaults and ADR-0039 remain authoritative; any QA-specific target change requires independent review.
