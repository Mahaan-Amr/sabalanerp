## اصلاحات محلی

1. پنج ایندکس partial افزایشی برای نشانگرهای شواهد خصوصی. بدون حذف، بازنویسی تاریخچه یا دورزدن مجوزها. شرط JSON با حفظ معنی قبلی روی ستون‌ها بررسی می‌شود؛ دیگر برای هر خواندن، دو سند بزرگ در یک JSON موقت کپی نمی‌شوند. literal ثابتِ کد امکان استفاده از ایندکس در prepared plan را حفظ می‌کند؛ ورودی کاربر وارد SQL خام نمی‌شود.
2. projection سبک برای فهرست/جست‌وجوی قراردادهای حسابداری. متن چاپی، گراف، audit گراف و اسنپ‌شات تحویل و پرداخت در این فهرست استفاده نمی‌شوند و دیگر واکشی نمی‌شوند. صفحه جزئیات و اصل اسناد تغییر نکرده‌اند. همه fallbackهای تاریخ قرارداد حفظ شده‌اند.
3. projection سبک مجموعه‌های خلاصه مالی؛ مبلغ‌ها، وضعیت‌ها، مانده‌ها و قواعد نمایش همان منطق قبلی را دارند.
4. یکسان‌سازی رقم فارسی/عربی/انگلیسی و شکل‌های عربی ی/ک برای جست‌وجوی فهرست قرارداد حسابداری، با استفاده از منطق موجود پروژه. شکست جست‌وجوی شماره فارسی قبل از اصلاح بازتولید شد.
5. مهلت محدود ۱۵ ثانیه و انتظار pool محدود ۵ ثانیه فقط برای ایجاد قرارداد. تراکنش اتمیک و retryهای قبلی حفظ شدند؛ timeout به retry خودکار جدید تبدیل نشده و timeout عمومی افزایش نیافته است.

## آزمون و اندازه‌گیری محلی

- تست اسکن JSON ابتدا با نبود ایندکس شکست خورد؛ سپس استفاده از هر پنج ایندکس تأیید شد. نشانگرهای nested، array، null، false و نبود نشانگر با شرط قبلی برابرند. روی fixture با نسبت نشانگر نزدیک ۱۵٪، دو اسکن بزرگ حدود ۰٫۱ میلی‌ثانیه شدند. این اعداد، benchmark محلی همان بخش هستند، نه latency production.
- روی ۲۵۸ قرارداد موجود محلی، زمان نمونه فهرست از ۲۱۳۲ میلی‌ثانیه به حدود ۱۶۰–۱۹۰ میلی‌ثانیه رسید. حجم JSON داخلی قراردادهای واکشی‌شده از ۱۰٬۸۲۳٬۹۴۴ بایت به ۳۵۳٬۴۱۳ بایت کاهش یافت؛ این حجم، پاسخ HTTP مرورگر نیست.
- خلاصه مالی همه ۲۵۸ ردیف در چند صفحه، تعداد قراردادها و همه تاریخ‌های projected با داده مرجع مقایسه شدند. جست‌وجوی شماره فارسی و انگلیسی خروجی یکسان داشت. query واقعی scope حسابداری نیز اجرا شد.
- تست ایجاد قرارداد با تأخیر عمدی ۵٫۵ ثانیه، ابتدا `P2028` داد و پس از اصلاح موفق شد. وجود graph و audit داخل تراکنش و نبود قرارداد پس از rollback بررسی شد. این fixture از قرارداد محلی است، نه بازپخش کامل پیش‌نویس production.
- تست بودجه تراکنش ثابت کرد `P2028` دوباره ارسال نمی‌شود.
- تست‌های accountingStatus، accountingPopulations، partnerAccounting، partnerReadSnapshot، crmCustomerSearch و contractSnapshotBoundary موفق بودند.
- کنترل مالکیت Prisma (`npm run architecture:check`) موفق بود؛ یک pool مشترک حفظ شده است.
- build نهایی backend (`tsc` و `tsconfig.cutover.json`) و `git diff --check` موفق بودند. تست کامل مرورگری production و اندازه‌گیری p95 پس از استقرار هنوز انجام نشده‌اند.

## باقی‌مانده و استقرار

- migration فقط آماده شده؛ روی جدول‌های واقعی local یا production اعمال نشده است.
- استقرار نیازمند اجازه جداگانه و مسیر `docs/operations/zero-data-loss-deployment.md` است: checkpoint محلی و نسخه رمزگذاری‌شده خارج سرور باید تأیید شوند و سپس migration و imageهای جدید در مرز maintenance اعمال شوند. تغییر داده یا تضعیف gate مجاز نیست.
- پس از استقرار: مقایسه p50/p95 بارگذاری و جست‌وجوی حسابداری با ترافیک عادی، بررسی صف/timeout، و یک تلاش کنترل‌شده برای ثبت پیش‌نویس اصلی با کنترل عدم تکرار لازم است.
- فیلترهای ترکیبی فهرست هنوز روی مجموعه summaryها اجرا می‌شوند؛ برای رشد بسیار بزرگ داده، read model صفحه‌بندی‌شده با حفظ دقیق جمع‌ها و فیلترهای وضعیت، مرحله بعدی است.
- مرورگر امکان پاسخ قدیمی جست‌وجو پس از پاسخ جدید را دارد (مشاهده کد، نه بازتولید قطعی). در این مجموعه هیچ رفتار frontend تغییر نکرده است.
