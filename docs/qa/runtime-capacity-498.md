# Runtime and storage capacity evidence for #498

## Compare equivalent workload windows

`RUNTIME_CAPACITY_OBSERVATION=1` in an approved backend process environment emits one `backend_capacity_window` JSON record per minute after the normal runtime reaches listen. Preserve the exact `APP_COMMIT` and align the host clocks. A record carries its UTC interval and process ID, event-loop delay p95 and maximum, endpoint RSS and main-heap usage, and aggregate duration and failure counts for each admitted, completed scheduler job. RSS includes native and worker memory. The 20 ms event-loop sampling resolution and the single memory observation per window limit what the sampler can see. Jobs that span windows are counted once in their completion window. Logs contain no job arguments, SQL, request contents or Prisma metric labels.

Join these intervals to [Accounting request observations](accounting-measurement-478.md) for the same instance and source commit. Record the local time zone, workload and request sample count per interval. Compare the same authorized routes and concurrency in quiet windows, peak interactive windows, and matched windows with relevant job completions. Summarize request p95 and errors alongside job count and maximum duration, loop latency, memory and pool waits. Select comparable success/error categories and include windows with missing or restarted processes in the evidence notes. Use the [Sales XLSX diagnostic](sales-xlsx-contention-20261123.md) for sub-minute memory peaks and report construction versus encoding. Temporal overlap alone cannot identify the responsible job.

The existing application's Prisma schema leaves the metrics preview disabled. Its standard-build windows report `poolWait: null`. `P2024` in the Accounting logs measures a pool timeout. The native Prisma 5.22 histogram measures pool checkout wait, including fast checkouts. `poolWait` reports the number of samples and total milliseconds added between snapshots plus the p95 bucket's upper bound. A null p95 can also mean zero checkouts or a percentile above the largest finite bucket. Restarted or missing counters produce a null window. The histogram is process-wide and does not attribute waits to a specific HTTP request or job.

Use the native histogram only in a short, isolated profiling candidate with the `metrics` preview enabled in its private generated client. The engine [enables recording at schema generation](https://github.com/prisma/prisma-engines/blob/605197351a3c8bdd595af2d2a9bc3025bca48ea2/query-engine/query-engine-node-api/src/engine.rs#L130), and [a snapshot replays retained histogram observations](https://github.com/prisma/prisma-engines/blob/605197351a3c8bdd595af2d2a9bc3025bca48ea2/libs/metrics/src/registry.rs#L155-L165). Bound the session duration and query volume, and record the profiling flag with its results. The sampler reuses the running application's client and publishes through the application log only. No metrics route or additional application database pool is needed. Keep production capacity conclusions separate from private profiling results.

## Audit growth and checkpoint headroom

Run [`runtime-audit-storage-census.sql`](../../scripts/qa/runtime-audit-storage-census.sql) with `psql -X -v ON_ERROR_STOP=1 --csv --file` and an authorized read-only connection. Scope and credential the existing environment per its operations guide. The SQL reads relation metadata and canned statistics in a read-only transaction with bounded statement and lock waits. It reports a fixed Accounting, Partner and recovery audit set with approximate live rows, inserts since stats reset, and physical table, index and total sizes. Missing relations yield nulls. Retain a timestamped aggregate receipt at the start and end of at least one comparable interval on the same database identity. Compare the byte difference independently of insert counters. A missing or changed reset timestamp leaves the insert rate unverified. Physical growth includes TOAST, indexes, reused pages and bloat. The query omits business fields and leaves all current history and retention policy in place.

For [#442](https://github.com/Mahaan-Amr/sabalanerp/issues/442), obtain a fresh observation from the protected operator for both the production filesystem used for builds and local restore staging and the physically independent checkpoint target. Use the [canonical preflight and checkpoint procedure](../operations/zero-data-loss-deployment.md) and [next-update runbook](../operations/protected-maintenance-next-update.md). Record measured-at UTC, retained release identity, available bytes, each required reserve and margin in bytes, accepted point count and hold state, and the independent restore result for the exact checkpoint. Apply the retention planner only through the documented boundary. Preserve active, held and referenced recovery artifacts and verified replacement evidence. Record go/no-go from the protected process.
