# Project-wide Cross-Workspace Duty Audit

## Purpose

This note maps current SabalanERP workspace relationships before the HR-specific duty implementation is generalized. It distinguishes a real duty—an accountable action with a due date and structured result—from a notification, a read-only data dependency, an operational queue, or a separate support/recovery workflow.

Primary sources are the current domain glossary, accepted ADRs, Prisma schema, backend routes/services, frontend workspace configuration, and tests. Older workspace overview documents are treated as discovery aids only when current code or domain decisions agree with them.

## Current platform boundary

- The interactive workspace shell currently recognizes Sales, CRM, Human Resources, Accounting, Inventory, Security/Guard, BI, and Logistics; Administration is outside that workspace enum (`frontend/src/contexts/WorkspaceContext.tsx:56`). The confirmed product decision is to make System Administration a permission-scoped duty destination without requiring a complete commercial workspace.
- The current duty database, API, engine, and UI are HR-named (`backend/prisma/schema.prisma:6434`, `backend/src/index.ts:261`, `frontend/src/features/hr-duties/DestinationDutyQueue.tsx:33`).
- Although `HrDuty.sourceType` is a string, response and surface adapters load only `HrWorkItem`; other sources are rejected (`backend/src/services/hrDutyEngine.ts:537`, `backend/src/services/hrDutySurface.ts:194`).
- The legacy creation and reconciliation HTTP paths are retired with HTTP 410, so the existing destination pages are not a wired general creation mechanism (`backend/src/routes/hr-duties.ts:121`).
- Existing destination pages cover the eight operational workspaces, but the page title remains HR-specific (`frontend/src/app/dashboard/sales/duties/page.tsx:1`, `frontend/src/features/hr-duties/DestinationDutyQueue.tsx:56`).

## Candidate relationship matrix

| # | Source → destination | Current business handoff | Classification | Current state and migration concern |
|---|---|---|---|---|
| 1 | Sales → Accounting | A Sales Contract becomes available for Accounting review and financial-record creation. | Candidate duty, decision required | Today Sales publishes `SALES_CONTRACT_READY_FOR_ACCOUNTING` to Accounting workspace users, but it is only a notification and is emitted at contract creation (`backend/src/routes/sales.ts:938`, `backend/src/services/notificationPolicy.ts:253`). Decide the precise eligibility event before creating an accountable duty, or every draft creation may create noise. |
| 2 | Sales → Accounting → Sales → Accounting | Seller requests correction; Accounting processes and decides; Sales receives one correction opportunity; Accounting verifies the saved difference. | Confirmed multi-stage duty chain | The accepted ADR and current implementation begin with an Accounting-owned correction request, conflicting with the newly agreed Seller-originated request (`docs/adr/0003-manager-approved-sales-correction-after-financial-approval.md:11`, `backend/prisma/schema.prisma:4269`). The old route must not remain as a second source of truth. |
| 3 | Accounting → Sales | A financial record was submitted or approved. | Notification/data state, not automatically a duty | `ACCOUNTING_RECORD_SUBMITTED` informs the resource owner and links to the contract; no Sales response is required (`backend/src/services/notificationPolicy.ts:263`, `backend/src/routes/accounting.ts:842`). Keep it an announcement unless a specific Sales action is defined. |
| 4 | Accounting → Accounting, affecting Sales | Deactivate, reactivate, or hard-delete a Sales Contract through a request and decision. | Governed workflow; same-workspace action, not inherently cross-workspace | Requests and decisions live in Accounting and mutate a Sales-owned record (`backend/src/routes/accounting.ts:427`, `backend/src/services/contractLifecycleService.ts:173`). Decide whether the unified duty engine also hosts intra-workspace approval stages; do not change ADR-0040 authority or dependency checks (`docs/adr/0040-audited-contract-deactivation-and-guarded-hard-deletion.md:3`). |
| 5 | Guard → Logistics | Guard admits a driver/vehicle into the shared loading-area pool; Logistics may reserve it. | Operational queue/data transition, not a person-assigned duty | ADR-0006 supersedes the earlier specific driver-request concept; reintroducing a Logistics→Guard request would conflict with the shared pool (`docs/adr/0006-loading-drivers-enter-shared-pool.md:3`, `CONTEXT.md:3222`). |
| 6 | Logistics → Accounting | Finalized allocation creates an Accounting Dispatch Candidate and open Accounting work item for accept/issue, reject, or return. | Existing true cross-workspace duty | Candidate and WorkItem already exist one-to-one (`backend/prisma/schema.prisma:2888`, `backend/src/services/dispatchAllocation.ts:213`). Migrate/project this work item rather than create a duplicate generic duty beside it. |
| 7 | Accounting → Logistics | Accounting rejects or returns an allocation; Logistics creates a successor revision while accepted siblings remain immutable. | True successor duty | The domain explicitly requires allocation-scoped rejection and successor work (`CONTEXT.md:3073`, `CONTEXT.md:3077`). The response and successor creation must commit atomically so the Accounting work item and Logistics action cannot disagree. |
| 8 | Logistics → Accounting | Logistics withdraws a pre-issuance candidate or requests void/replacement after waybill issuance. | Mixed: command before issuance; duty after issuance | Pre-issuance withdrawal is Logistics-owned and closes the Accounting item; an issued waybill can only be voided by Accounting (`CONTEXT.md:3085`, `CONTEXT.md:3089`). Model only the post-issuance Accounting action as a duty. |
| 9 | Accounting/driver → Guard | A confirmed, valid exit authorization permits Guard to record physical exit. | Operational authorization/queue, not automatically an assigned duty | Guard owns the physical fact and must not treat Logistics finalization or document issuance as exit (`CONTEXT.md:3146`, `CONTEXT.md:3150`). A due assignment is justified only if Guard has a distinct queue item requiring acknowledgement. |
| 10 | Guard → Accounting | A verified physical return requires Accounting to post the linked negative dispatch correction. | True cross-workspace duty | Returned Dispatch Reconciliation changes dispatched quantity only after Accounting posts the correction (`CONTEXT.md:3162`). The Guard evidence is immutable input, not something Accounting may edit. |
| 11 | Guard + Accounting | Manual outage exit requires dual, distinct approvals and preserved outage evidence. | Specialized multi-party duty | Dispatch dual control forbids collapsing the approvals; a generic permission rule allowing one actor to perform multiple steps must not override this workflow (`CONTEXT.md:3134`, `backend/src/services/__tests__/dispatchDocumentAuditRecovery.test.ts:322`). |
| 12 | HR → Accounting | Finance recording and finance approval for hiring compensation. | Existing HR-originated cross-workspace duties | These action definitions already target Accounting (`backend/src/services/hrDutyEngine.ts:51`). Preserve their minimum-necessary envelope and migrate them as source adapters rather than HR-special cases. |
| 13 | HR Payroll → Accounting | An Approved Payroll Run summary is handed off for posting and settlement. | True cross-workspace duty | Accounting consumes an immutable summary and may not edit employee calculation lines (`CONTEXT.md:2629`, `docs/adr/0023-separate-payroll-calculation-from-accounting-settlement.md:3`). |
| 14 | Accounting → HR Payroll | Accounting requests a supplemental or reversal payroll correction. | True reverse duty | ADR-0023 assigns correction of payroll lines back to HR rather than Accounting mutation (`docs/adr/0023-separate-payroll-calculation-from-accounting-settlement.md:3`). Source/result schemas must identify the posted obligation without exposing unnecessary payroll evidence. |
| 15 | Employee/HR → Responsible Supervisor workspace | Routine leave approval or schedule proposal requires action by the effective responsible supervisor. | True permission/assignment-scoped duty | The approver is effective-dated organizational responsibility, not a generic role (`CONTEXT.md:2049`, `CONTEXT.md:2213`). Destination may be the supervisor's operational workspace; absence/delegation/escalation must retain the snapshotted route. |
| 16 | HR → Security | Approved leave and expected schedules affect attendance and guard coverage. | Data consequence; only derived coverage remediation is a task | Security consumes the approved result and never approves leave (`CONTEXT.md:2069`, `docs/adr/0014-hr-owns-leave-security-consumes-consequences.md:3`). | 17 | Security → Supervisor/HR/Payroll | Actual attendance derives Overtime Candidates; the supervisor confirms, HR may correct classification, Payroll consumes approved overtime. | Multi-stage duty chain with immutable source evidence | Security records physical truth but cannot determine pay entitlement (`CONTEXT.md:2205`, `docs/adr/0019-overtime-approval-separates-attendance-from-payroll.md:3`). | 18 | Responsible Supervisor → HR | Proposed work-schedule change requires HR preparation and approval. | True cross-workspace duty chain | ADR-0032 requires supervisor proposal, HR Processor preparation, and a separate HR Manager approval (`docs/adr/0032-require-separated-work-schedule-preparation-and-approval.md:3`). This strict separation is workflow-specific and must survive a platform rule that permits combined actions elsewhere. |
| 19 | HR/supervisor → workspace/data owners → Administration | ERP User provisioning after Hire Conversion. | Confirmed multi-owner duty chain with a permission-scoped Administration destination | Access is requested by the responsible supervisor, approved by relevant owners, and fulfilled by an authorized User administrator (`CONTEXT.md:2485`). Administration will receive a protected queue without becoming a complete commercial workspace. |
| 20 | HR/supervisor → safety/equipment/data owners; Security verifies | Pre-Activation Activity Permit approvals. | Conditional multi-party duties plus read-only verification | HR and supervisor always approve; extra owners depend on scope; Security verifies but does not approve (`CONTEXT.md:2561`). The engine needs parallel prerequisite results without giving every participant the full HR record. |
| 21 | HR → multiple owners | Offboarding creates equipment return, payroll settlement, ERP access revocation, and physical access revocation tasks. | Strong project-wide duty aggregate candidate | Each task retains a distinct owner and may remain overdue without keeping employment active (`CONTEXT.md:2117`). Inventory, Accounting, Administration, and Security ownership must be confirmed individually before implementation. |
| 22 | CRM → Sales | A potential project can supply customer and responsible-seller context when converted into a Sales Contract. | Conditional duty only while another actor's readiness transition leaves conversion outstanding | Readiness recorded by another actor creates one Sales conversion duty for the responsible seller; atomic conversion by that seller creates no redundant duty. | 23 | Inventory → Sales | Sales reads product catalog facts, pricing inputs, and availability where implemented. | Read-only data dependency today | Current Inventory documentation largely describes catalog/integration and planned stock management; no authoritative action-response workflow exists (`docs/workspaces/inventory/README.md:124`). Do not invent low-stock or catalog-request duties until their source records and owners are defined. |
| 24 | Sales/Accounting/CRM → BI | BI reads sales, payment, delivery, customer, product, discount, and seller facts. | Read-only analytical dependency; never a duty by default | BI v1 is management-only analysis (`docs/workspaces/bi/README.md:1`). An anomaly may later create a duty in the owning operational workspace, but BI itself should not become a competing writer or task owner. |
| 25 | Any workspace ↔ Support/Recovery | Support tickets, deployments, recovery approvals, incidents, and SLA escalation. | Separate platform workflows | The domain already keeps destination duties separate from support work and notifications (`CONTEXT.md:169`). ## Cross-cutting implementation conflicts

1. **Rename is insufficient.** `HrDuty`, `HrDutyEnvelope`, `hrDutyEngine`, `hrDutySurface`, `/api/hr-duties`, and `features/hr-duties` encode HR ownership and a single source adapter.
2. **Current creation gap.** Existing generic-looking destination pages do not prove a live project-wide creation path; legacy create/reconcile routes are retired.
3. **Duplicate work truth.** Accounting Dispatch, HR Work Items, Accounting Corrections, Contract Lifecycle Requests, onboarding tasks, notifications, and operational queues already model work differently. The generic engine should project or adapt the authoritative source record, not create an unrelated second lifecycle.
4. **Workflow-specific actor rules.** Contract correction permits one non-requesting actor with both grants to perform both Accounting stages. General Manager and ADMIN are explicitly allowed to perform both compensation or Payroll stages through separate audited actions. Manual outage dual control still requires two distinct people, and other accepted workflow-specific separation rules must not be weakened accidentally.
5. **Notification is not duty state.** Existing Sales/Accounting notifications must remain delivery records triggered from authoritative duty events; their unread state must not drive the navigation badge.
6. **Administration is missing from the workspace enum.** The decision is resolved, but implementation still needs a first-class permission-scoped destination, protected navigation, queue, and badge behavior without manufacturing a commercial workspace.
7. **No-duty consumers.** BI stays read-only, Inventory catalog visibility stays data-only unless a concrete correction action exists, and CRM creates a duty only when readiness leaves conversion waiting for another actor.
8. **Superseded Guard routing.** The shared driver pool must not be replaced by the older specific driver-request model.

## Recommended discussion order

1. Sales ↔ Accounting contract readiness and correction.
2. Logistics ↔ Accounting dispatch candidate, rejection, void, return, and correction.
3. Guard ↔ Logistics/Accounting operational boundaries and dual control.
4. HR ↔ Accounting compensation and payroll.
5. Supervisor/HR/Security leave, schedules, attendance, and overtime.
6. Onboarding, access provisioning, permits, and offboarding across Administration, Inventory, Accounting, and Security.
7. Explicit confirmation that CRM, Inventory, and BI relations remain data-only until a concrete action source exists.
