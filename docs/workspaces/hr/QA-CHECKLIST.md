# چک‌لیست کامل QA فضای کاری منابع انسانی

این چک‌لیست چرخه اصلی `Candidate → Job Application → Personnel → Employment Relationship → optional User` را پوشش می‌دهد. هر آزمون باید با کاربر، زمان، داده ورودی، نتیجه واقعی و مدرک تصویری یا شناسه درخواست ثبت شود.

## ۱. آماده‌سازی و نقش‌ها

- [ ] `HR_PROCESSOR`، `HR_MANAGER`، `HIRING_MANAGER`، `HR_PAYROLL_PROCESSOR`، `HR_PAYROLL_MANAGER`، `FINANCE_RECORDER` و `FINANCE_MANAGER` به کاربران جداگانه واگذار شوند.
- [ ] کاربر دارای دسترسی عمومی HR ولی فاقد اختیار کسب‌وکاری نتواند تأیید مدیریتی انجام دهد.
- [ ] یک نفر نتواند سند، وثیقه، قرارداد یا بسته جبران خدماتی را که خودش آماده/بارگذاری کرده تأیید کند.
- [ ] غیرفعال‌کردن یک اختیار، اقدام‌های بعدی آن کاربر را فوراً مسدود کند ولی تاریخچه قبلی را تغییر ندهد.
- [ ] جایگاه فعال با ظرفیت خالی، واحد سازمانی، شغل، محل کار، مرکز هزینه و جایگاه سرپرست آماده باشد.
- [ ] `PUBLIC_APP_URL` در production یک URL معتبر HTTPS باشد.
- [ ] قالب `SMS_IR_HIRING_INVITATION_TEMPLATE_ID` اختصاصی و دارای `Name`، `Link` و `Code` باشد.
- [ ] اجرای production با نبود URL عمومی یا قالب اختصاصی پیامک متوقف و خطای تنظیمات روشن ثبت شود.

## ۲. ناوبری و مدل ذهنی

- [ ] داشبورد و منوی HR عنوان `جذب و پرونده‌های متقاضیان` را نشان دهند.
- [ ] داشبورد و منوی HR عنوان `پرسنل و روابط استخدامی` را نشان دهند.
- [ ] توضیح صفحه جذب، مسیر متقاضی تا تبدیل و فعال‌سازی را بیان کند.
- [ ] توضیح صفحه پرسنل، هویت پایدار فرد را از رابطه استخدامی تاریخ‌دار جدا کند.
- [ ] هیچ مسیر عادی با عنوان مبهم «ثبت پرسنل و استخدام» نمایش داده نشود.

## ۳. ایجاد پرونده متقاضی

- [ ] HR Processor یا HR Manager بتواند برای جایگاه فعال و دارای ظرفیت پرونده ایجاد کند.
- [ ] نام، نام خانوادگی، موبایل معتبر `09xxxxxxxxx` و جایگاه الزامی باشند.
- [ ] کد ملی اولیه اختیاری باشد ولی در صورت ورود، الگوریتم اعتبارسنجی شود.
- [ ] جایگاه غیرفعال رد شود.
- [ ] موبایل نامعتبر، نام خالی و کد ملی نامعتبر با پیام فارسی روشن رد شوند.
- [ ] پرونده باز تکراری برای همان Candidate و Position با `409` و لینک/شناسه پرونده موجود رد شود.
- [ ] Candidate موجود با همان کد ملی دوباره ساخته نشود.
- [ ] ایجاد پرونده رویداد `APPLICATION_CREATED` بسازد.

## ۴. پیامک، لینک و OTP

- [ ] پیامک واحد شامل نام متقاضی، لینک شخصی `/apply/{token}` و کد شش‌رقمی باشد.
- [ ] دامنه لینک دقیقاً از `PUBLIC_APP_URL` تولید شود و در production از HTTPS استفاده کند.
- [ ] بازکردن لینک، صفحه عمومی ورود OTP را بدون نیاز به حساب ERP نشان دهد.
- [ ] OTP صحیح فقط همان Job Application را باز کند.
- [ ] OTP نادرست پیام مناسب بدهد و پرونده را باز نکند.
- [ ] پس از پنج OTP نادرست، تلاش بعدی ۱۵ دقیقه با `429` مسدود شود.
- [ ] OTP صحیح پس از قفل و پایان ۱۵ دقیقه شمارنده خطا را پاک کند.
- [ ] همان لینک و OTP در بازه هفت‌روزه روی دستگاه دیگری قابل استفاده باشد.
- [ ] session متقاضی بیش از تاریخ انقضای دعوت معتبر نماند.
- [ ] بازکردن لینک متقاضی B در مرورگری که session متقاضی A دارد، OTP متقاضی B را مطالبه کند و پرونده A را نشان ندهد.
- [ ] ارسال مجدد توسط HR دعوت قبلی را فوراً لغو کند.
- [ ] لینک/OTP قبلی پس از ارسال مجدد با `410` رد شود.
- [ ] لینک منقضی یا لغوشده پیام تماس با HR را نشان دهد و دکمه self-resend نداشته باشد.
- [ ] صدور دعوت جدید، پیش‌نویس ذخیره‌شده متقاضی را حذف نکند.
- [ ] رویدادهای ارسال دعوت و تأیید OTP با actor مناسب ممیزی شوند.

## ۵. فرم عمومی متقاضی

- [ ] صفحه پس از OTP، عنوان جایگاه درخواستی و درصد تکمیل را نشان دهد.
- [ ] ذخیره پیش‌نویس با داده ناقص مجاز باشد.
- [ ] خروج و ورود مجدد، آخرین پیش‌نویس را بازیابی کند.
- [ ] فیلدهای الزامی نام، نام خانوادگی، نام مستعار/پاسخ عدم وجود، تولد، محل تولد، نظام وظیفه، اطلاعات پدر، تأهل، نشانی، کدپستی، موبایل، تلفن منزل، تحصیلات، شبکه اجتماعی و سابقه بیمه کنترل شوند.
- [ ] کدپستی دقیقاً ۱۰ رقم باشد.
- [ ] موبایل دقیقاً الگوی ایران را رعایت کند.
- [ ] برای متأهل، تعداد فرزند و شغل همسر الزامی شوند؛ برای مجرد اجباری نباشند.
- [ ] برای ایرانی، کد ملی معتبر الزامی باشد.
- [ ] برای تبعه خارجی، نوع و شماره هویت خارجی الزامی و کد ملی غیرلازم باشد.
- [ ] وضعیت سابقه تأمین اجتماعی فقط yes/no باشد و به‌تنهایی استخدام را مسدود نکند.
- [ ] نوع و مدت همکاری فقط مقادیر پشتیبانی‌شده را بپذیرند.
- [ ] ارسال نهایی بدون پذیرش اظهارنامه و نام کامل رد شود.
- [ ] نام اظهارنامه با نام کامل فرم پس از نرمال‌سازی فاصله‌ها یکسان باشد.
- [ ] ارسال نهایی نسخه را `SUBMITTED` و پرونده را `SCREENING` کند.
- [ ] IP، user-agent، زمان، نام اظهارکننده و نسخه فرم حفظ شوند.
- [ ] فرم ارسال‌شده قفل شود و ذخیره مستقیم بعدی با `409` رد شود.

## ۶. بازگشت برای اصلاح

- [ ] HR فقط یک فرم `SUBMITTED` را با دلیل و فهرست فیلدهای موجود برگرداند.
- [ ] بازگشت بدون دلیل یا بدون فیلد رد شود.
- [ ] نام فیلد ناشناخته رد شود.
- [ ] متقاضی فقط فیلدهای مشخص‌شده را ویرایش کند.
- [ ] تلاش API برای تغییر فیلد خارج از فهرست با `422` رد شود.
- [ ] ارسال مجدد نسخه جدید بسازد و نسخه قبلی را حفظ کند.
- [ ] دلیل، فیلدهای اصلاحی، زمان‌ها و رویداد بازگشت در تاریخچه بمانند.

## ۷. مدارک و تطبیق هویت

- [ ] فقط HR Processor بتواند سند هویتی ثبت کند.
- [ ] منبع مشاهده `اصل مشاهده شد` یا `کپی دریافت شد` الزامی باشد.
- [ ] PDF/JPEG/PNG واقعی تا ۱۵MB پذیرفته و پسوند جعل‌شده رد شود.
- [ ] production بدون malware scanner یا override صریح، فایل را رد کند.
- [ ] جایگزینی مدرک نسخه جدید بسازد و نسخه قبلی را پاک نکند.
- [ ] دانلود سند فقط برای HR Processor/Manager مجاز و ممیزی شود.
- [ ] HR Processor برای هر فیلد نتیجه تطبیق و یادداشت ثبت کند.
- [ ] mismatch یا unverifiable حل‌نشده، تأیید نهایی هویت را مسدود کند.
- [ ] فقط HR Manager مستقل بتواند identity clearance را `APPROVED` کند.
- [ ] HR Manager نتواند سندی را که خودش به‌عنوان processor ثبت کرده خودتأیید کند.

## ۸. ارزیابی و محرمانگی

- [ ] ارزیابی DISC/BIG FIVE/EQ/OTHER فقط برای نقش‌های مجاز قابل ثبت و مشاهده باشد.
- [ ] متقاضی هیچ یادداشت داخلی، ارزیابی روان‌شناختی یا توصیه استخدامی را نبیند.
- [ ] Finance داده هویتی یا ارزیابی خارج از scope خود را نبیند.
- [ ] HR جزئیات محرمانه ابزار وثیقه، ضامن، محل نگهداری و اسکن مالی را نبیند.
- [ ] مشاهده و دانلود داده حساس رویداد ممیزی بسازد.

## ۹. پیشنهاد جبران خدمات

- [ ] فقط Hiring Manager بسته ردیفی ریالی با حداقل یک مؤلفه بسازد.
- [ ] عنوان خالی، مبلغ منفی/اعشاری/غیرعددی و آرایه خالی رد شوند.
- [ ] جمع کل از ردیف‌ها محاسبه شود و مقدار دستی مستقل نداشته باشد.
- [ ] HR/Payroll Processor بسته را آماده و طبقه‌بندی کند.
- [ ] HR/Payroll Manager پس از processor و با تفکیک وظیفه تأیید کند.
- [ ] Finance Manager پس از تأیید HR/Payroll تعهد مالی را تأیید کند.
- [ ] متقاضی پیش از هر دو تأیید، پیشنهاد را نبیند.
- [ ] متقاضی با همان session عمومی و نام کامل پیشنهاد را بپذیرد.
- [ ] پذیرش، snapshot تأییدشده را تغییرناپذیر و زمان پذیرش را ثبت کند.

## ۱۰. وثیقه و تعهدات

- [ ] قالب وثیقه فقط توسط Finance Manager ساخته/فعال/غیرفعال شود.
- [ ] Finance Recorder فقط پس از پذیرش پیشنهاد قالب مناسب را اعمال کند.
- [ ] هر قلم الزامی نوع، مبلغ/شناسه لازم، تحویل اصل، محل نگهداری و فایل معتبر داشته باشد.
- [ ] Finance Manager نتواند قلم ثبت‌شده توسط خودش را خودتأیید کند.
- [ ] رد قلم دلیل روشن داشته و نسخه جایگزین تاریخچه را حفظ کند.
- [ ] clearance نهایی تا تأیید همه اقلام الزامی مسدود بماند.
- [ ] HR فقط پیشرفت و نتیجه هماهنگی را ببیند، نه جزئیات محافظت‌شده مالی.

## ۱۱. تبدیل Candidate به Personnel

- [ ] تبدیل پیش از تأیید هویت، تأیید وثیقه، پذیرش پیشنهاد و تأییدهای HR/Finance رد شود.
- [ ] تاریخ شروع برنامه‌ریزی‌شده الزامی باشد.
- [ ] جایگاه غیرفعال یا بدون ظرفیت در تراکنش تبدیل رد شود.
- [ ] تبدیل اتمیک Personnel، رابطه `PLANNED`، Assignment اصلی، بیمه اولیه و onboarding را بسازد.
- [ ] خطا در هر بخش هیچ رکورد نیمه‌کاره یا ظرفیت مصرف‌شده باقی نگذارد.
- [ ] Candidate با کد ملی Personnel موجود به همان هویت متصل و duplicate ساخته نشود.
- [ ] تبدیل User نسازد.
- [ ] Application فقط پس از موفقیت کامل `CLOSED/HIRED` و `convertedAt` دریافت کند.
- [ ] رابطه استخدامی `hiringApplicationId` یکتا داشته باشد.
- [ ] پرونده جذب، Personnel و وضعیت رابطه/تخصیص را همان‌جا نشان دهد.
- [ ] پرونده پرسنلی لینک `ایجادشده از پرونده جذب` را نشان دهد.
- [ ] لینک‌های رفت و برگشت به رکورد درست برسند.
- [ ] ارزیابی محرمانه در پروفایل عمومی Personnel کپی نشود.

## ۱۲. قرارداد، حقوق، بیمه و onboarding

- [ ] قرارداد فقط پس از تبدیل و توسط Finance Recorder بارگذاری شود.
- [ ] شماره، شروع، ترتیب تاریخ پایان و فایل معتبر قرارداد کنترل شوند.
- [ ] جایگزینی قرارداد نسخه جدید بسازد؛ فقط آخرین نسخه قابل تأیید باشد.
- [ ] Finance Manager بارگذار همان قرارداد نتواند آن را تأیید کند.
- [ ] تأیید قرارداد clearance و task متناظر را کامل کند.
- [ ] HR/Payroll Manager مشارکت حقوق را با تاریخ مؤثر ثبت کند و task آن کامل شود.
- [ ] HR وضعیت بیمه را میان NOT_STARTED/IN_PROGRESS/ACTIVE/EXEMPT مدیریت کند.
- [ ] بیمه ACTIVE بدون تاریخ مؤثر رد شود.
- [ ] بیمه ACTIVE یا EXEMPT task بیمه را کامل کند ولی activation blocker نباشد.
- [ ] HR Manager بتواند task اضافی با owner، موعد و blocker مشخص بسازد.
- [ ] فقط دارنده همان owner authority بتواند task را کامل کند.
- [ ] تکمیل task مدرک‌نیاز، بدون evidence لازم طبق سیاست رد شود.

## ۱۳. فعال‌سازی

- [ ] رسیدن خودکار تاریخ شروع رابطه را Active نکند.
- [ ] فعال‌سازی پیش از تاریخ شروع رد شود.
- [ ] identity، collateral، contract و compensation همگی باید APPROVED باشند.
- [ ] payroll participation باید وجود داشته باشد.
- [ ] همه taskهای activation blocker باید COMPLETE یا WAIVED باشند.
- [ ] خطای فعال‌سازی فهرست همه پیش‌نیازهای ناقص را نشان دهد.
- [ ] فعال‌سازی موفق رابطه و Personnel را Active و `activatedAt` را ثبت کند.
- [ ] صفحه `پرسنل و روابط استخدامی` برای رابطه متصل به جذب، دکمه فعال‌سازی مستقیم نشان ندهد.
- [ ] فراخوانی مستقیم API وضعیت برای فعال‌کردن رابطه PLANNED متصل به جذب رد شود.
- [ ] بازگشت از تعلیق برای رابطه قبلاً فعال، تاریخچه جذب را تغییر ندهد.

## ۱۴. رد، انصراف و لغو

- [ ] بستن پرونده فقط outcomeهای REJECTED/WITHDRAWN/REQUEST_CANCELLED را بپذیرد.
- [ ] دلیل بستن الزامی و در تاریخچه حفظ شود.
- [ ] پرونده دارای رابطه Active از مسیر بستن جذب رد و به offboarding هدایت شود.
- [ ] پرونده تبدیل‌شده ولی فعال‌نشده، رابطه و assignment را پایان دهد و ظرفیت را آزاد کند.
- [ ] همه دعوت‌های باز هنگام بستن لغو شوند.
- [ ] در صورت وجود وثیقه تحویل‌شده، بستن تا ثبت تحویل، مدرک و تأیید مستقل Finance Manager مسدود شود.
- [ ] پروفایل عادی Candidate برای talent bank بماند و داده حساس در جستجو ظاهر نشود.

## ۱۵. ثبت استثنایی پرسنل

- [ ] کاربر فاقد `HR_MANAGER` فرم ثبت استثنایی را نبیند.
- [ ] همان کاربر با فراخوانی مستقیم endpoint نیز `403` بگیرد.
- [ ] endpoint عادی قدیمی `/api/hr/personnel` دیگر ایجاد انجام ندهد.
- [ ] فرم با عنوان روشن `ثبت استثنایی پرسنل` نمایش داده شود.
- [ ] فقط DATA_MIGRATION، HISTORICAL_CORRECTION و ORGANIZATIONAL_TRANSFER پذیرفته شوند.
- [ ] دلیل کمتر از ۱۰ نویسه رد شود.
- [ ] duplicate name نیازمند تأیید صریح و کد ملی تکراری با conflict رد شود.
- [ ] ثبت موفق Personnel، رابطه، Assignment و `EXCEPTIONAL_PERSONNEL_REGISTERED` را در یک تراکنش بسازد.
- [ ] audit شامل actor، منبع، دلیل، زمان، رابطه، جایگاه، وضعیت و وجود/عدم وجود User باشد.
- [ ] کارت Personnel منشأ و دلیل ثبت استثنایی را نشان دهد.
- [ ] ثبت استثنایی هیچ پرونده جذب جعلی نسازد.

## ۱۶. مدیریت پس از استخدام

- [ ] Personnel و User هویت‌های جدا بمانند؛ اتصال User اختیاری و یکتا باشد.
- [ ] رابطه‌های استخدامی یک فرد هم‌پوشانی نداشته باشند.
- [ ] تاریخ Assignment کاملاً داخل بازه Employment Relationship باشد.
- [ ] در هر لحظه فقط یک Assignment اصلی وجود داشته باشد.
- [ ] Assignment ثانویه ظرفیت مصرف و Acting ظرفیت مصرف نکند.
- [ ] انتقال جایگاه، Assignment قبلی را تاریخ‌دار ببندد و سابقه را حذف نکند.
- [ ] کاهش ظرفیت زیر occupancy فعال/متعهد رد شود.
- [ ] پایان استخدام از تغییر وضعیت ساده رد و به offboarding هدایت شود.
- [ ] برنامه کاری جدید نسخه مؤثر جدید بسازد و سابقه قبلی را حفظ کند.

## ۱۷. امنیت، ممیزی و پایداری

- [ ] token و OTP خام در دیتابیس ذخیره نشوند؛ فقط hash نگهداری شود.
- [ ] logهای production موبایل را mask و OTP/token را افشا نکنند.
- [ ] فایل خصوصی URL عمومی مستقیم نداشته باشد و path traversal رد شود.
- [ ] هر دانلود حساس مجوز را دوباره در backend کنترل کند.
- [ ] CORS فقط مبدأهای تنظیم‌شده را بپذیرد.
- [ ] دو تبدیل هم‌زمان نتوانند ظرفیت را بیش از حد مصرف یا دو Personnel بسازند.
- [ ] دو تأیید هم‌زمان نتیجه ناسازگار نسازند.
- [ ] خطاهای unique/serialization پیام قابل اقدام و بدون stack trace حساس بدهند.
- [ ] زمان‌ها در دیتابیس UTC و در UI با نمایش محلی سازگار باشند.
- [ ] reload، back/forward و موبایل، وضعیت فرم عمومی را خراب نکنند.
- [ ] صفحه عمومی RTL، دارای label، focus قابل مشاهده، ورودی عددی مناسب و خطای قابل خواندن باشد.

## ۱۸. سناریوی پذیرش انتهابه‌انتها

- [ ] یک پرونده واقعی آزمایشی از ایجاد تا SMS، OTP، پیش‌نویس، ارسال، اصلاح، هویت، پیشنهاد، وثیقه، تبدیل، قرارداد، payroll، onboarding و activation کامل شود.
- [ ] در هر مرحله با نقش اشتباه اقدام و ردشدن آن ثبت شود.
- [ ] پس از activation، رفت‌وبرگشت میان پرونده جذب و Personnel درست باشد و هیچ داده محرمانه‌ای نشت نکند.
- [ ] یک سناریوی REJECTED پیش از تبدیل کامل و retention آن بررسی شود.
- [ ] یک سناریوی WITHDRAWN پس از دریافت وثیقه، بازگشت و تأیید تحویل را کامل کند.
- [ ] یک ثبت استثنایی مجاز و یک تلاش غیرمجاز اجرا شود؛ audit ثبت موفق و پاسخ `403` تلاش غیرمجاز بررسی شوند.
