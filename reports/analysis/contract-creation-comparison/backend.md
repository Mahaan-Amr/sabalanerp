# Backend comparison — current source, 2026-10-07

Scope: inspected current backend routes, persistence services, Prisma schema, approval/payment/output consumers and relevant ADRs. No production code or existing worktree files changed. This report and fresh probe are audit artifacts. Docker Compose inspection failed because Docker Desktop's Linux engine pipe does not exist; no runtime/integration DB claims are made. Local pure-function tests and a fresh production-function probe ran successfully.

## Important version boundary

The ordinary wizard uses `backend/src/routes/sales.ts:1153` -> `services/contractService.ts:782`. `routes/contracts.ts:187` is the legacy contract API and is not authority for the current creation wizard. Ordinary new commercial flow is `commercialFlowVersion=1` with no Partner identity (`ordinaryContractLifecycle.ts:24`). Partner new cases use Case `commercialFlowVersion=1` and paired customer SalesContract `commercialFlowVersion=2` (`cases/aggregate.ts:635`, `cases/linkedPair.ts:131`). Historical Partner cases retain a separate explicit `/finalize` branch; the current branch explicitly rejects that endpoint (`routes/partner-cases.ts:919`). Comparing legacy statuses alone would therefore give incorrect conclusions.

## Findings and unresolved risks

1. **Intentional and high-impact**: two economic obligations, two payment purposes, wholesale inquiry gate, clear debtor/audience segregation, different deadline origin and dispatch settlement policy must survive any UI/code sharing. Unifying them would create financial/privacy defects.
2. **Confirmed architectural divergence, severity requires runtime**: ordinary creation has no observable command-level replay guarantee; Partner does. Ambiguous response/retry and lease release race require a DB-backed duplicate-submit test before labeling a duplication bug.
3. **Confirmed source asymmetry, impact unverified**: Partner computes expired status in read/command gates; ordinary has a periodic expiry writer/cancellation worker. Need prove whether idle Partner expiration cancels old links, emits events and reaches persisted expiry automatically. Predicate blocks mutation, so do not claim expired contract can still be accepted without repro.
4. **Validation seam to examine**: ordinary application party identity checks names and project ownership, not card blacklist/lock/profile restrictions in that function. DB retained-card trigger resolves deleted-customer concern. Need inspect effective permission/DB persona guards and call real endpoint for locked/blacklisted/cross-owner customers before any bypass claim.
5. **Document precedence resolved**: ADR-0060's customer-independent explicit commitment is superseded for the new Partner flow by ADR-0113. ADR-0113's early second-review wording is superseded by latest documented acceptance line 180. These are historical rules, not current defects.
6. **No universal readiness claim**: Passing pure tests says nothing conclusive about two-client races, real SQL constraints, pricing-duty delivery, mutable-history isolation, actual invoice issuance/receipt posting/financial void, SMS, PDFs or browser UI. Existing Docker stack was unavailable during this audit.

## Safe repair boundaries

First map desired UI parity separately from economic parity; retain central authorizers, Case root, stable productRowId, revision/hashes and allowlisted customer outputs. Share physical product graph/calculation and canonical UI fields where their meaning matches. Add isolated existing-stack scenarios for create retry, expiry, locked customer, incomplete plans and full ordinary-vs-Partner approval/dispatch combinations before repairing apparent differences. Never route Partner customer contract through ordinary `createContract`/item-mutation API merely to reuse wizard UX.
