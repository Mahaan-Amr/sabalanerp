# #438 controller target audit — 2026-11-12

This is a source and read-only host audit for the owner-approved independent Linux rehearsal route. It is **not** a completed QA adapter or a #432 rehearsal admission. No Docker action, key transfer, remote write, or production action was made.

## Existing controller can target a genuinely separate Linux host

`deploy/scripts/deploy.sh` selects `docker-compose.prod.yml`, the `sabalanerp` project from `/opt/sabalanerp`, six named release services, `/opt/sabalanerp/.deploy-state/deployment.lock`, and FD9. On a genuinely isolated native Linux Docker host with a private `/opt/sabalanerp` clone and daemon, those exact names and paths do not collide with production or the existing Windows `sabalanerp-local` project. Retaining the original controller is preferable to adding a generic project, service, Compose-file, or lock override. Native daemon PID/config and process namespace proof, exact prior six-image import, private ingress, QA-only volumes and source identity still need independent verification before any run.

The production Compose Nginx service publishes ports 80 and 443 on all guest interfaces. The QA host must prove those listeners cannot be reached publicly before starting it. The existing Nginx template needs TLS certificate files for `${DOMAIN}` and resolves both ERP and Inquiry names. QA DNS/hosts and certificates must be private; `verify_public_maintenance()` tests `https://${DOMAIN}/` and `https://${INQUIRY_DOMAIN}/` for real 503. No production domain or public address may be used by QA.

The long-running backend Compose definition sets `NODE_ENV=production` and includes external-effecting SMS and other configuration. The restored production-state data and production application decryption keys cannot be paired with live external credentials. A reviewed QA environment must use sandbox/no external delivery and a host egress boundary, while retaining the keys needed to decrypt and verify protected data. This cannot be asserted from the current local development env.

## Independent backup namespace is the remaining controller adaptation

The unchanged backup path is **not safe to point at production custody**. `deploy/scripts/storage-preflight.sh` requires SSHFS source `sabalan-backup@<host>:/checkpoints`, fixed users `sabalan-backup` and `sabalan-backup-ops`, and an existing project recovery volume. It calls `storage-preflight.mjs --mode apply` and then the restricted backup-host `preflight` command before builds/maintenance. `deploy/scripts/backup-retention-host.mjs` requires the operations user and root cwd `/opt/sabalanerp`; it validates a remote retention response whose storage root is exactly `/srv/sabalanerp-recovery/checkpoints`. Reusing the production backup host/accounts/root for QA could modify the live backup retention namespace. A separate QA checkpoint root and independent remote owner are mandatory, with distinct credentials and a plan-bound host/root/user selection or an entirely separate SSH/SFTP backup endpoint running the existing fixed account contract.

The Windows W: and Z: drives are the same SMB server `\\172.16.10.13\ShareVolume` (Z: is a `CNC` subdirectory), with 269,042,679,808 bytes free. TCP 445 is reachable and TCP 22 is not. This is physically off the proposed WSL2 QA host, but it cannot satisfy the current SSHFS/remote-owner protocol unchanged. A QA-only SMB capacity/readback adapter would need to prove off-host identity and preserve the remote verification/retention invariants; a mere mapped drive or fixture receipt is insufficient.

A dedicated namespace on the existing backup host would use `/srv/sabalanerp-qa-recovery/checkpoints`, distinct `sabalan-qa-backup` and `sabalan-qa-backup-ops` accounts/keys, `/run/lock/sabalan-qa-backup-storage.lock`, a separately installed `/opt/sabalanerp-qa-recovery` owner, and a QA-only SSHFS mount. The narrow adapter would accept these identities only from a root-owned, exact-host QA plan and leave production's fixed users/root/response checks untouched. The QA retention owner must see only its QA root; merely changing the client mount path while retaining the production operations account would still allow cleanup in production custody.

Capacity lower bounds for that namespace follow `scripts/deployment-capacity.mjs`: `checkpointBytes = ceil(sourceBytes × 1.15)` and `remoteBytes = ceil(checkpointBytes × 1.05)`. The measured remote requirement for current production shape was 2,711,393,585 bytes, implying an estimated checkpoint size about 2,582,279,604 bytes. The current backup host has 3,077,361,664 bytes free. Keeping one QA checkpoint at the measured capture size of 1,476,223,433 bytes and passing the second run's remote preflight needs at least 4,187,617,018 bytes free at the start, a deficit of at least 1,110,255,354 bytes plus sidecars/logs. Using the conservative estimated checkpoint size raises that minimum to 5,293,673,189 bytes, a deficit of at least 2,216,311,525 bytes. Retaining two conservative QA points and being ready for another preflight requires about 7,875,952,793 bytes free, a deficit of about 4,798,591,129 bytes. These are lower bounds, not an execution capacity certificate: migrations can grow data, and a fresh source measurement plus safety headroom is mandatory. A provider expansion of at least 10 GB is a practical planning target; the current disk has no usable unallocated extent.

Read-only source-equivalent retention planning found no safe capacity recovery. `planRemoteCheckpointRetention` admits a legacy archive for deletion only after `hasHealthyIndependentCheckpointDrill` validates a v1 HEALTHY/COMPLETE independent drill, then preserves the newest two and every hold. All nine remote `.sabrec.json` sidecars and their objects were present. Only the October 13 and 14 sidecars had a `lastDrill.status` of HEALTHY, but neither had the required `phase: COMPLETE`; the other seven had no healthy drill. There were no `online-...` checkpoint directories. Thus the policy has zero eligible delete IDs and zero reclaimable checkpoint bytes from these points. A subsequent canonical `storage-preflight.mjs --mode plan` under the backup-host FD9 lock recorded its normal capacity audit line and returned `containers: []`, `images: []`, and 3,038,597,120 bytes available. No cleanup was applied.

The remaining host space is not disposable without separate review. `/root/sabalan-recovery-private` uses 9,159,852,032 bytes for named drill, transfer, and native QA evidence (the largest drill is 3,238,100,992 bytes). `/var/lib/docker` uses 5,387,939,840 bytes; its sole image belongs to a healthy running drill PostgreSQL container, and the canonical plan found no removable image or container. `/var/log/journal` uses 3,288,543,232 bytes. Forty-two archived system journal files total 3,271,557,120 bytes, with dates October 18 through November 12, during the current boot. Thirty-three archived files dated through November 5 total 2,592,079,872 bytes. These journals may contain incident evidence; they are outside canonical checkpoint/Docker retention.

If operations independently approves moving journal evidence, an exact candidate is to copy **all** archived journal files plus a per-file SHA-256 manifest over SSH into a private directory on the workstation's fixed `D:` volume (173,427,593,216 bytes free), then verify every transferred file's hash, count, size, and readback before a bounded `journalctl --vacuum-time=7d` on the backup host. Preserve the active journal, backup audit logs, and the off-host archive. A seven-day cutoff could reclaim approximately 2.5 GB, subject to actual journal timestamps and journald's own vacuum selection. No archive transfer or vacuum has been executed; until independent custody and evidence review, this is a NO-GO cleanup proposal rather than a capacity certificate.

### Reviewable archive and vacuum candidate (not authorized for execution)

1. Freeze the source set under a host operations lock separate from the checkpoint lock. Inventory regular archived `*@*.journal` files only beneath the resolved `/var/log/journal/<machine-id>/` directory. Record machine ID, hostname, boot ID, each relative path, byte size, modification time, SHA-256, and the journal's first/last entry times; reject symlinks or a changed file set. Run `journalctl --verify` on the selected source files and retain its result. This is a copy operation, not a checkpoint retention action.
2. Create a dated private directory on the workstation's fixed `D:` volume, outside every production/QA source tree. Remove inherited ACLs and grant only the owner account and local Administrators full access; confirm the effective ACL before copying. Verify encryption at rest on that volume or place the archive in a separately encrypted container with a recoverable key; ACL alone does not establish encrypted custody. The `D:` BitLocker state was not established in this audit. Keep the recovery key out of the archive and store it in approved independent custody.
3. Copy the exact manifest and archived files over authenticated SSH into that directory without changing backup-host originals. Hash every destination file by reading it from `D:` and compare to the source manifest, byte count, relative paths, and metadata. Run `journalctl --verify` against the copied files if the workstation has a compatible journal reader, or on a separate Linux reader using the copied files. A transfer command's success alone is not readback proof. Preserve a second copy or a documented recovery route if workstation loss is in scope; `D:` is off-host but is one physical custody point.
4. Independently review whether any October–November journal interval is under incident/legal hold. Keep all held files on the backup host unless the hold owner explicitly approves the verified off-host archive as equivalent evidence. Confirm a recovery operator can locate, decrypt, and read the archive without the original backup host, and record the manifest, readback result, custody path, review sign-off, and pre-vacuum `df -B1 /` in a restricted evidence note. The current active journal and `/var/log/sabalanerp-backup` audit trail are excluded from vacuum consideration.
5. Only after that review, use journald's bounded `journalctl --vacuum-time=7d`, never `rm` or blanket Docker prune. Re-inventory files and compare the actual removed paths to the archived manifest; re-check `journalctl --verify`, backup-host services, canonical checkpoint sidecars/objects, audit trail, and `df -B1 /`. Stop if any file outside the reviewed set disappeared or if free space is below the fresh source-based QA capacity preflight. Do not infer future third-run capacity from first-run success.

The measured upper bound for a seven-day candidate based on file modification dates is 33 files / 2,592,079,872 bytes through November 5; journald uses journal time ranges, so actual reclaim may differ. At the PLAN's 3,038,597,120 bytes free, that upper-bound scenario gives 5,630,676,992 bytes, only 337,003,803 bytes above the conservative first-plus-second threshold. The theoretical maximum after removing all 42 archived files is 6,310,154,240 bytes, still 1,565,798,553 bytes short of the conservative two-retained-plus-third-preflight threshold. Archive/vacuum approval therefore cannot replace a durable capacity solution for continuing releases.

## W: SMB bridge option (design only)

A direct CIFS mount on the QA application host is not an admissible shortcut. The protected controller's `storage-preflight.sh` and `install-independent-backup-mount.mjs` require an exact SSHFS transport, a distinct `sabalan-backup-ops` owner, and a remote preflight. `backup-retention-host.mjs` and backend `deploymentBackupRetention.ts` bind the receipt to that owner's PID, root FD9 lock, fixed checkpoint root, and SSH process closure. `deployment-checkpoint.ts` checks that receipt before upload and after metadata readback; local retention checks it again after checkpoint. A changed path and hash through a local CIFS mount would leave those controls unproven.

The technically plausible W: route needs an additional independent Linux backup-owner bridge, separate from both the QA application host and the production backup host. It would reach `172.16.10.13` over private authenticated SMB3, mount a dedicated QA-only directory at `/srv/sabalanerp-recovery/checkpoints`, and run the original restricted SSH/SFTP backup-owner protocol with QA-specific host keys, transfer/operations keys, and accounts. The parent `/srv/sabalanerp-recovery` must stay a root-owned native directory for OpenSSH chroot; the mounted checkpoint directory must be writable only by the transfer identity. The existing production backup host and its nine points remain untouched. The Windows SMB server itself cannot run the Linux FD9/SSH owner contract, and TCP 22 was not available on it during this audit.

That bridge needs a narrow QA-only backup-host preflight change: the current `backup-preflight-root.sh` passes `--storage-root /srv/sabalanerp-recovery` to `storage-preflight.mjs`. If only its `checkpoints` child is CIFS, this measures the bridge's native root disk and can falsely pass remote capacity. The QA owner must prove the exact expected CIFS mount source, server identity, target, and restrictive mount options, then pass the checkpoint mountpoint as the measured storage root while retaining FD9, reference-aware cleanup, audit, and fail-closed result. No generic client-side mount/root/account override is indicated; production scripts and defaults remain fixed.

Before qualification, the real bridge must prove private network reachability from the QA Linux host to SSH owner and from owner to SMB server; SMB authentication and encryption/signing; dedicated QA share ACLs and encryption at rest; correct chroot/UID semantics; unique QA keys; capacity reported from CIFS; resumable upload, atomic rename, full stream readback from off-host storage, metadata readback, and independent restore; owner retention under FD9 with held/newest points preserved; and failure behavior on SMB disconnect. Windows `Get-SmbConnection` access was denied, so dialect, signing/encryption, and remote identity remain unverified. There is no authorized bridge or proof that the independent QA host can reach this private LAN. Therefore W: is a conditional design, **NO-GO for the full #432 protected seam today**. No W: write, bridge installation, or adapter code was executed.
