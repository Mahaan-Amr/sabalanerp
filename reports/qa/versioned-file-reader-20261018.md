# Independent materialization of per-write file cuts

`SealedVersionedFiles` reads the actual Node producer's hash-pinned immutable seal, selected version records and predecessor lineage. It streams selected independent objects into a new private `intent.json` / `files/` / `complete.json` wrapper, with separate output read-back and fsync. It never reads mutable heads, pending operations or live source bytes. It has no admission lease, capture, prune, traffic or healthy application-point API. The declared live path is metadata used solely to prohibit overlapping destinations.

The final candidate is frozen in `versioned-file-reader-review-r3-20261018.json` and `.codex-versioned-file-reader-review-r3.patch`. Six real Linux tests passed in `versioned-file-reader-f4671b324280815a0bebab8854d4d388.json`, with all four canonical container/image/start identities unchanged. Actual Node PUT/replacement/deletion cuts restore exact Unicode/control-character paths and decimal-containing bytes after live paths and mutable heads have been renamed away. A later unresolved intent does not invalidate the selected prior cut. Wrong hashes, existing targets, malformed lineage and live-source targets are refused. Missing, same-size damaged, symlinked, hardlinked and FIFO objects never produce a complete receipt.

The real Python reader was SIGSTOPped after its first output bytes were written. While stopped, the application completed a new file write, attachment deletion and a competing actual EX seal. SIGCONT then completed the original 17 MiB file and original attachment from the first cut. No SQL, database/container termination or fabricated gate was involved.

Both reviewers found that the first reader could restore into the live source. Spec review also found that its aggregate 512 MiB predecessor cutoff was incompatible with the producer's per-key history limits. The two new regressions failed against the retained exact r1 source (`versioned-file-reader-source-r1.py.txt`, SHA `318fcb20c1ebd6d6344b8d7153b1e6cef7c07b1941abca2e8d5f1b1429f37cf9`): four tests passed and these two failed in `versioned-file-reader-red-20261018.json`. The corrected reader rejects target overlap before target filesystem access. It verifies one record at a time in at most four concurrent chains, settles all started work before returning on failure, and retains only bounded selected-head/object metadata. There is no aggregate history refusal absent from the producer.

The long-history regression independently writes real immutable records; the actual Node publisher then acknowledges generation 9,999 for nine keys and creates the selected seal. The corrected reader verifies all 89,991 records, including 557,822,664 independently seeded metadata bytes. It took 234,778 ms outside the write pause; the full six-test run took 250,846 ms. This deliberately extreme component test is not a production recovery budget. Actual release admission still requires measured complete application restore time, capacity, image identities and all domain/privacy gates.

`versioned-file-reader-native-closure-20261018.json` binds the actual staged r1/r3 reader and fixture hashes and verifies both runs' helpers absent, every fixture's actual gate available and all work journals QUIESCENT. Original negative evidence is retained. Existing protected source/points, application databases and routing are unchanged. Full writer/upload/privacy coverage, bounded coherent capture, continuous independently verified PostgreSQL recovery and full new-chain restoration remain required.
